Paged KV、Prefix Sharing、COW 与 Swap

本节目标：用操作系统页表和引用计数理解项目最核心的内存工作，并能证明 COW/Swap 的正确性。

1. 连续 KV 分配的问题

若为每个请求预留最大上下文，会产生大量内部碎片；若按实际长度连续增长，扩容和外部碎片又很难管理。Paged KV 把逻辑 token 序列切成固定大小 block，通过 Block Table 映射到不连续物理块。

Sequence A logical: [0] [1] [2-tail] │ │ │ Physical pool: [7] [3] [9] Sequence B logical: [0] [1] [2-tail] │ │ │ [7] [3] [12] 共同 prefix 引用 7、3；分叉后 tail 分别指向 9、12。

block size 小：尾部浪费少、映射灵活，但 metadata、查表和 kernel/copy 次数增加。block size 大：元数据少、连续搬运友好，但 partial tail 浪费更多，COW 复制粒度更大。本项目默认 16，是工程折中，不是数学最优常数。

2. PrefixIndex 与最长匹配

PrefixIndex 用 token block 内容定位可复用前缀。匹配必须以 token 序列为准，而非原始字符串；不同模板/空格可能 tokenize 不同。最长前缀匹配决定能跳过多少 prefill，但引用物理块前必须增加 refcount，淘汰时也不能释放仍被引用的块。

3. Partial-tail sharing 为什么需要 COW

只共享完整块最简单，但会浪费最后不足 16 token 的公共 tail。共享 partial tail 能提高命中，问题是下一个 token 会写入同一物理块。如果直接写，所有共享者内容被污染。

写前条件：refcount(p)=1
若 refcount(p)>1：allocate(q) → copy valid prefix p→q → writer remap p→q → dec_ref(p) → write(q)

顺序非常重要。先减旧引用再成功分配/复制，失败时可能丢数据；先切映射但复制未完成，读者可能看到半成品。实现需要把操作视作事务，并在 CUDA 异步场景用 event 保证 copy 完成后才发布。

4. 引用计数和 ABA/UAF

refcount 只解决“多少逻辑映射仍引用物理块”，不自动解决异步 GPU 命令仍在使用该块。Host 看到 refcount 归零时，先前 stream 中的 kernel 可能尚未完成。安全方案包括：同 stream 有序释放、event 延迟回收、generation/version 防止旧句柄把新分配块误认为原对象。

5. Preemption 与 Swap 的事务语义

抢占不是删除。Swap-out 应先把完整 KV 和元数据写入 backing store，校验成功后才释放 resident block；Swap-in 应先预留目标容量、读取并校验，再原子恢复映射。文件存储建议临时文件写完后 rename，避免崩溃留下“名字存在、内容不完整”的 checkpoint。

失败点安全结果
Host allocation 失败保持 resident KV；回退重算或拒绝抢占
File write 中断旧 checkpoint 仍有效；临时文件可清理
CUDA copy 失败不发布新映射；记录错误并保持/回滚旧状态
恢复时容量不足不部分恢复；继续 swapped 或回退 recompute
个人贡献证据：server-kv-block-manager.*、server-kv-capacity-planner.*、server-kv-swap-store.*、src/llama-kv-cache-paged.cu 以及对应 tests/bench。面试时不要把 vLLM 的实现说成自己的；应说“借鉴 paging 思想，在固定 llama.cpp 上游中实现并接入真实 KV 路径”。
不变量练习：写出 allocate/share/append-COW/release 四个操作前后，free_count、refcount 总和和 Block Table 引用数必须满足的关系；再设计一个“CUDA copy 成功但 host commit 前崩溃”的恢复策略。

主动回忆

为什么 partial-tail sharing 比完整块共享更难？

解析难点是共享可变尾块的隔离，COW 将“共享读”转换为“独占写”。
