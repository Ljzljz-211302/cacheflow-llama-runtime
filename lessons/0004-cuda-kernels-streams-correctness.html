Lesson 04 · CUDA / 体系结构 · 60 min

Kernel、Memory、Stream、Event 与正确性

本节目标：能读懂项目 CUDA KV 路径，解释为什么“写了 CUDA”不等于“性能更好”，以及如何证明异步代码正确。

1. 执行层次

00D 已介绍 grid、thread block 和 thread。GPU 由多个 SM（Streaming Multiprocessor，流式多处理器）组成，thread block 会被分配到某个 SM。一个 block 内线程可通过 shared memory（块内共享的高速内存）交换数据，并用 barrier（屏障）等待彼此到达同一步。

Warp是 NVIDIA GPU 成组执行线程的硬件粒度，通常包含 32 个线程。同一 warp 走不同条件分支时，硬件往往分批执行不同路径，这叫分支分歧。

索引常见写法：

size_t i = blockIdx.x * blockDim.x + threadIdx.x;
if (i < n) dst[i] = src[mapping[i]];

面试需说明：边界检查防 OOB；连续线程访问连续地址有利于 coalescing；但一个纯 copy kernel 未必比 cudaMemcpyAsync 快，后者有专用实现和更低通用索引开销。

2. 项目为何同时有 direct-copy 与 staging kernel

映射完全不重叠时，逐块 memcpy 通常更直接。若 scatter/gather 的源与目标可能重叠或同一源被重复映射，原地复制可能覆盖尚未读取的数据。staging 先保存快照，再写目标，获得类似 memmove 的语义。项目实验的负结果是：无重叠时 staging kernel 反而慢，因此生产路径只在需要 snapshot 语义时使用。

3. Stream 的 happens-before

同一 stream 内命令按提交顺序执行；不同 stream 之间没有自动顺序保证。Host 的 kernel launch 通常异步返回，所以“函数返回”不代表 GPU 已完成。

stream A: copy-out ── record(event E) ──────────── stream B: wait(E) ── restore ── record(done) host: enqueue ───────────────── wait(done) ── publish mapping

page-locked host memory 是异步 Host↔Device 传输/重叠的重要条件。过早释放 pinned buffer 会 UAF；过度 cudaDeviceSynchronize() 虽然“安全”，却摧毁并发。更好的边界是精确 event + 生命周期所有权。

4. Event 计时回答什么

两个 event 包围同一 stream 的操作，测的是设备时间区间，不包括请求排队前的全部 Host 调度和网络时间。项目同时保留：

证据能回答不能回答
CUDA Event指定 stream 操作设备耗时完整请求 latency、occupancy 根因
nvidia-smi 100ms sample粗粒度 busy/idle 趋势短 kernel 精确利用率
Engine traceprepare/plan/execute/commit 时间归属warp/SM 级瓶颈
SSE TTFT用户侧首 token 结果具体哪个 kernel 导致变化

5. 正确性工具

Compute Sanitizer 的 memcheck 查越界、未对齐和部分 API/硬件错误；racecheck 主要检查 shared memory hazard；它们不是性能 profiler，也不能证明没有所有 Host 侧竞态。项目还需要 canary、随机 mapping、逐元素 CPU oracle、allocation failpoint 和端到端真实模型 smoke。

高频追问：“racecheck 通过是否证明没有 race？”答：不证明。官方说明 racecheck 聚焦 shared memory hazard；跨 stream 生命周期、Host mutex、文件事务仍需 event 设计、状态机测试和故障注入。
