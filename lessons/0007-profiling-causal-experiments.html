怎样证明一次系统变化真的造成了结果

Profiling（性能剖析）是测量程序时间、资源和执行事件，寻找性能花在哪里。本节学习如何把 profiler 数据与受控实验组合成因果链，并识别噪声、选择偏差和错误统计。

1. 为什么 profiler 截图不是因果证据

相关表示两个量一起变化；因果表示改变一个因素会引起另一个结果变化。看到 TTFT 高时 GPU busy 也高，只能说明相关；它们可能共同由更长 prompt、温度、后台进程或运行顺序造成。

干预（intervention）是实验者主动改变策略；中介（mediator）是策略影响结果途中应被改变的变量，例如 prefill chunk 和 KV copy。因果实验要尽量保持其他条件不变，并确认干预真的穿过预期中介。

Intervention Mediators Outcome upstream ↔ always → decisions → prefill chunks/tokens → KV launch/copy/Event + GPU samples → Engine execute → SSE TTFT P95

如果 policy 参数改变但 decision counter 没变，干预无效；如果 scheduler 改变但没有 CUDA 中介，不能声称 CUDA 路径导致；如果只见 CUDA noise、Engine/TTFT 不变，也不能声称有系统影响。

2. Paired Latin 设计

每个 trial 将 upstream 与 always 配成一对，以同一 workload/seed 比较；Latin 顺序轮换避免总是先跑某策略而把热机/温度趋势混入策略效应。统计应先算每对差或比，再对 paired effect 求中位数。

曾修正的错误：“learned 的独立中位数 ÷ upstream 的独立中位数”不是 paired estimator。两个中位数可能来自不同 trial，破坏配对。当前短门禁按同一 trial 计算 ratio 后取中位数。

3. 冷启动与长驻实验为何分开

fresh-process A/B 回答“重启后短 trace 是否安全、回归是否受控”；53-wave 单 PID 回答“在线模型能否积累数据并持续利用”。把二者混在一起，会把冷启动探索税误判成稳态性能，或把长驻模型状态泄漏到独立 trial。

4. Material effect 门槛

任何采样都有抖动。CUDA 因果门禁除了要求中介，还要求 |ΔTTFT|≥5ms 且 |ΔEngine execute|≥1000µs。这不是统计显著性的替代，而是先拒绝工程上无意义的微小波动。更完整研究还应报告置信区间、功效分析和更多硬件。

5. 最终结果怎么解释

always 相对 upstream 的配对中位差：决策 +15、prefill chunk +23、prefill token −145、KV copy −2.519MB、CUDA Event −0.260ms、GPU busy +1.19%，但 Engine execute +31.23ms、TTFT P95 +44.79ms。

正确结论不是“CUDA kernel 变慢”，因为 copy/Event 实际下降；也不是“GPU busy 上升导致 TTFT”，因为 100ms 采样太粗。更稳健的解释是：策略改变了 batch/分块/排队结构，局部 KV 搬运改善没有转化为端到端尾延迟改善。进一步定位需要 Nsight Systems timeline、Compute occupancy/roofline 和更多 paired trials。

6. 指标契约

decision/observation/fallback/drift 是累计 counter；terminal predicted benefit/uncertainty 是 gauge。抓 phase 差值时只对 counter 做减法，gauge 保留末值；counter 若回退说明进程重启或抓错实例，验收应失败。

主动回忆

为什么先求 paired ratio 再取中位数？

解析配对利用同 trial 的共同条件；它不保证通过，只让估计更符合实验设计。
