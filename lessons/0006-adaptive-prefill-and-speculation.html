Adaptive Prefill 与 Speculative Decoding

本节目标：解释两个“加速策略”为何都需要在线控制，以及项目实现与论文算法的边界。

1. Chunked Prefill 的基本权衡

长 prefill 一次完成，矩阵大、吞吐可能好，却形成长迭代，阻塞 decode。切成 c token 的块，可在块间插入 decode，改善 TTFT/TPOT 尾部；但 chunk 太小会增加调度、kernel launch、KV 操作和重复 bookkeeping。

iteration cost(c) ≈ fixed_launch + compute(prefill_tokens≤c, decode_batch) + scheduling_overhead(c)

最优 c 依赖 backend、活跃 decode、剩余 prompt、KV 压力和目标 iteration 时间。固定 64/128/256 不可能对所有状态最优，因此项目维护按 backend bucket 的在线 cost model，并保留 chunk=0 upstream greedy 安全动作。

2. 控制器为何要避免振荡

若只看上一轮耗时：上一轮过慢就减 chunk，下一轮过快又增 chunk，可能来回振荡。常见稳定手段包括 EWMA、hysteresis、安全范围和最小观察量。项目负结果显示 CPU 在线动作曾劣于所有固定候选，因此加入 backend 分桶和 2% 回归门禁；这是“从负结果收紧控制器”的面试亮点。

3. Speculative Decoding 原理

论文中的推测解码让廉价 draft 模型提出多个 token，target 模型一次并行验证，并通过接受/拒绝采样保持目标分布。速度来自“target 验证一段 token”比“串行生成同样数量 token”便宜。

粗略加速由接受长度和验证成本决定：

speedup ≈ accepted_tokens_per_verify / (draft_cost + verify_cost relative to one target step)

接受率低时，draft 成本和验证浪费会使其更慢；batch、模型大小和 memory bandwidth 都会改变 break-even point。

4. 本项目的边界

项目使用 N-gram speculation controller，不是训练/部署独立 draft Transformer。它根据命中/接受反馈动态选择 speculation depth，并有固定策略对照。能展示的是“在线深度控制、反馈和回退”；不能声称实现了论文完整双模型采样算法。
