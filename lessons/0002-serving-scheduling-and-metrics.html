系统每一轮该让哪些请求运行

多个用户同时请求时，系统必须选择下一轮处理谁。这个选择过程叫调度；本节从排队开始，再引出按模型迭代调度、状态机和服务指标。

1. 为什么不能“凑一批请求，全部跑完”

Batch（批）是把多个请求的数据合在一次模型计算中，让 GPU 同时处理。若一个 batch 中的请求必须全部生成结束后才重新组队，这叫 request-level batching（按完整请求组批）。

请求输出长度未知且差异大，短请求会被排在前面的长请求挡住，这叫 head-of-line blocking（队首阻塞）；期间新请求也不能加入。Orca 系统提出把调度粒度降到一次模型迭代：每执行一轮模型后重新观察完成、到达、取消和资源状态，这叫 iteration-level scheduling（按模型迭代调度）。

prepare：收集可运行状态、取消/超时、资源快照 ↓ plan：选择 slot、decode token、prefill chunk、KV 动作（尚不产生不可逆副作用） ↓ execute：调用 runtime / llama_decode / CUDA ↓ success ↓ failure commit：发布 token、推进状态 abort：丢弃未提交变化、进入恢复路径

这就是本项目 server_inference_iteration 的状态机。Engine是组织整轮推理的核心模块；commit表示确认并发布成功结果，abort表示放弃本轮未提交变化。核心不变量：execute 只执行冻结计划；只有 commit 后外界才看见状态推进。

2. 调度对象与常见策略

Request是一次用户请求及其取消/超时生命周期；sequence是模型内部正在增长的一条 token 序列；slot是 server 里承载一条活跃 sequence 的执行位置。把三者混成一个对象，会让取消、多个生成分支、swap 恢复和 slot 复用难以保持一致。

策略优点失败模式
FCFS（先到先服务）简单、到达顺序可解释长 prefill 阻塞 decode
最短剩余优先平均延迟低长请求可能饥饿，且剩余长度未知
Cache-aware（缓存感知）复用公共开头，减少 prefill过度追逐 cache 会破坏公平性
Aging（等待加分）等待越久加分，防止饥饿权重过大时牺牲局部效率
SLO-aware（服务目标感知）优先救即将超时请求持续过载时所有请求都“紧急”

SLO（Service Level Objective，服务目标）是系统承诺努力满足的指标目标，例如“95% 请求 TTFT 不超过 500ms”。它不是每次都绝对满足的硬件定律。

本项目分数可以用下式解释，而不必声称它是全局最优：

score = reuse gain − prefill cost − eviction cost + aging bonus − SLO risk

面试官若问“为什么不用动态规划求最优”，应答：真实系统状态持续变化、请求长度未知、动作时间受 GPU/batch 影响，精确全局优化成本过高；项目选择可解释在线启发式，并用 shadow plan、回退和实测约束风险。

3. 背压、取消、Deadline

背压发生在准入边界：队列满时明确拒绝，避免无限排队导致内存和 latency 崩溃。取消要求请求进入 terminal state 后不再被调度，并安全释放/递减 KV 引用。Deadline不是简单排序字段：过期请求应在 prepare 阶段清除，不能执行后才发现超时。

4. TTFT、TPOT、吞吐为何必须一起看

只看总 latency 会掩盖交互体验；只看 TTFT 可能通过让首 token 很快、后续极慢来“作弊”；只看吞吐会牺牲单请求尾延迟。P95 关心尾部，但小样本分位数非常不稳定，因此项目使用 fresh-process 多 trial 并保留原始记录。

面试陷阱：“TPS 提升 10% 所以方案更好”不成立。必须同时给 workload、并发、上下文、TTFT/TPOT/latency 分位数、质量和硬件，并承认 CUDA mixed workload 的历史结论反号。
