1. 先把项目说清楚

1.1 一句话定位

CacheFlow Runtime 是一个基于固定 llama.cpp 上游版本、进入真实 llama-server → llama_decode → KV memory → CUDA 热路径的单机 LLM Serving / AI Infra 项目，核心工作覆盖推理迭代事务、缓存感知调度、块级 KV 生命周期、事务 Swap、在线收益门控和 CUDA KV Remap。

1.2 30 秒版本

我基于固定版本 llama.cpp 改造了真实推理热路径，而不是在外层套一个 Agent。控制面把每轮推理拆成 prepare、plan、execute、commit/abort；KV 侧实现 Prefix Block 共享、引用计数、尾块 COW、容量规划和 Host/File/CUDA Swap；CUDA 侧实现进入真实 Qwen KV tensor 的 128-bit Gather/Scatter Remap。算子通过 CPU oracle、Compute Sanitizer、真实模型输出对照和配对微基准验证。小规模 Remap 提升约 49%–53%，但这不是端到端推理加速，而且当前没有实现 PagedAttention。

1.3 三分钟组织方式

  1. 问题：多轮/并发请求重复 Prefill，KV 占用大，长 Prefill 会阻塞 Decode，抢占与共享又会产生复制和一致性问题。
  2. 架构：Engine 统一拥有调度、容量、KV、Swap 和迭代状态；HTTP 层只做协议与组合。
  3. 机制：Continuous Batching + Aging；Block Table + PrefixIndex + refcount；partial-tail COW；事务 Swap。
  4. 底层：真实 KV tensor 的 descriptor-driven CUDA Remap，对齐路径使用 uint4，异常路径安全回退。
  5. 证据：单元/性质测试、Sanitizer、真实 Qwen、真实应用、配对实验。
  6. 边界：单机单 GPU、0.5B 模型；Remap 微基准不等于端到端；Full 统计门禁存在波动；未实现 PagedAttention。

2. 从一次聊天请求开始

模型是根据输入数字计算下一个 token 概率的参数化函数；推理是用训练好的参数做前向计算；训练才会计算梯度并更新参数。项目处理的是推理和服务，不训练模型。

  1. 浏览器发送 HTTP 请求，包含消息、最大生成长度等参数。
  2. 应用检索本地资料，构造完整 prompt。
  3. Tokenizer 把文本切成整数 token。token 是词表中的子词单元，不严格等于汉字或单词。
  4. 请求进入 llama-server 队列，Scheduler 将它绑定到可执行 slot。
  5. Prefill 处理已有 prompt，产生每层 K/V 并写入 KV Cache。
  6. Decode 每轮通常为每条活跃序列产生一个新 token，新 token 又成为下一轮输入。
  7. Sampler 根据 logits 选择 token；logits 是 softmax 前的未归一化分数。
  8. 服务器用 SSE 分块发送文本；SSE 是服务器到浏览器的事件流。
  9. 生成完整结束后才把 assistant 消息写入 SQLite，避免断流留下半条回答。
HTTP/SSE → 应用检索 → Tokenizer → Request Queue → Slot ↓ Prefill（处理整段 prompt） ↓ 写入 K/V Decode（每轮生成一个 token）↺ ↓ Sampling → 文本流 → SQLite
闭卷输出：不用任何英文缩写，向非计算机同学解释一次提问为什么要经过“切数字、先读题、逐字续写、保存中间记忆”四步。

3. Transformer 与自回归推理

3.1 向量、矩阵、Embedding

向量是一列数，表示对象在多个特征方向上的坐标；矩阵是批量做线性变换的规则。点积 q·k 把两个向量压成一个数，可理解为方向匹配程度。Token ID 本身没有大小语义，Embedding 表按 ID 查出长度为 d_model 的向量。

3.2 Self-Attention

Q = XWQ, K = XWK, V = XWV
Attention(Q,K,V) = softmax(QKT/√dh + Mask)V

原始依据：Attention Is All You Need。

  • Q：当前位置想从历史中找什么。
  • K：历史位置提供的匹配索引。
  • V：匹配后真正聚合的信息。
  • √d 缩放：避免维度增大使点积方差过大、softmax 饱和。
  • Causal Mask：禁止看未来 token，保证自回归生成合法。

3.3 KV Cache

Decode 第 t 步的旧 token K/V 与前一步相同。KV Cache 保存每层历史 K/V，新一轮只计算新 token 的 Q/K/V，并让新 Q 读取历史 K/V，避免重复投影。代价是显存随层数、上下文和并发线性增长。

3.4 MHA、MQA、GQA

结构Q headKV head特点
MHAHH每个 Q head 独立 K/V，容量最大
MQAH1全部 Q head 共用 K/V，最省显存
GQAHHkv若干 Q head 共用一组 K/V，折中质量与带宽

真实 Qwen2.5-0.5B 日志是 14 个 Q head、2 个 KV head、24 层、head_dim 64，属于 GQA。CUDA 微基准的 32 层、8 KV head、head_dim 128 是合成传输布局，不能冒充模型结构。

3.5 RoPE、RMSNorm、SwiGLU

  • RoPE：按位置旋转 Q/K 的二维分量，使点积携带相对位置；通常 V 不旋转。
  • RMSNorm：按均方根缩放向量，不减均值，稳定层间数值尺度。
  • SwiGLU：常写为 down(silu(gate(x)) ⊙ up(x)) 的门控前馈结构。

3.6 Prefill 与 Decode

PrefillDecode
输入多个 prompt token每序列通常一个新 token
并行性大矩阵，GPU 利用率较高窄矩阵，常受带宽/launch 影响
指标主要影响 TTFT主要影响 TPOT
调度风险长 Prefill 阻塞 DecodeDecode 过多挤压新请求

3.7 量化、GGUF、GGML

量化用更少 bit 表示权重，降低模型文件、内存和带宽，但引入近似误差。Q4_K_M 是一类 K-quant 权重量化；本项目相关 KV 路径按 FP16 讨论。GGUF是模型张量与元数据文件格式；GGML是 llama.cpp 的张量计算和后端基础设施。

4. KV Cache 公式与手算

KV bytes = 2 × L × T × Hkv × Dhead × element_bytes × Nseq

第一个 2 是 K/V 两份；L 是层数；T 是每序列 token；Hkv 是 KV head；Dhead 是 head 维度；FP16 每元素 2 byte。

真实模型示例：2×24×2×64×2 = 12,288 byte/token = 12 KiB/token。单序列 4096 token 约 48 MiB，32768 token 约 384 MiB。还没算权重、计算 buffer 和碎片。
闭卷手算：32 层、8 KV head、head_dim 128、FP16、上下文 8192、并发 4，需要 4 GiB KV。

5. LLM Serving：从单请求到多用户

5.1 四个容易混淆的对象

Request
一次 HTTP 任务，包含 prompt、采样参数、deadline 等。
Sequence
一条正在生成的 token 序列；一个请求在某些算法中可能产生多条候选 sequence。
Slot
服务器中承载 sequence 状态的执行位置，拥有 prompt/KV/计时等状态。
Iteration
服务循环的一轮。Continuous Batching 在 iteration 边界增删 sequence，而不是等整批请求全部完成。

5.2 Static Batching 为什么不适合生成

不同请求的 prompt 长度和生成长度不同。若固定一批请求直到全部结束，短请求会等待长请求，GPU 还会为结束序列留下空洞。Iteration-level / Continuous Batching 允许每轮把已完成序列移出、新请求加入，并为活跃序列各推进少量 token。

系统参照：Orca, OSDI 2022。

5.3 四个核心指标

指标定义用户感受可能的作弊方式
TTFT请求到第一个输出 token 的时间“多久开始回答”优先新请求但饿死旧请求
TPOT首 token 后相邻输出 token 的平均/分位间隔“打字是否流畅”牺牲 TTFT 只服务 decode
Latency请求到完整结束“多久答完”只测很短输出
Throughput单位时间处理 token/请求数系统总能力/成本无限增大 batch，牺牲尾延迟

P95 是 95% 样本不超过的值，反映尾部体验；它不是“最慢 5% 的平均值”。吞吐和延迟往往冲突，因此不能只报一个指标。

5.4 Chunked Prefill

把长 prompt 的 Prefill 切成多个 chunk，与已有 Decode 交错。chunk 太大：单轮占用久，TPOT 变差；太小：iteration、kernel launch 和调度开销增加，吞吐下降。最优值取决于 CPU/CUDA、上下文、并发、模型和硬件。

5.5 背压、取消与 Deadline

  • 背压：队列或生成槽达到上限时拒绝/延后新请求，防止内存无限增长和尾延迟雪崩。
  • 取消：客户端断流后要向上游 llama-server 传播取消，释放 slot/KV；只关闭浏览器连接不够。
  • Deadline：超过时限的任务不应继续消耗稀缺 GPU；但清理必须保持状态一致。

6. 项目架构：所有权与迭代事务

OpenAI HTTP/SSE │ server_context：协议、组合、llama_decode callback │ server_inference_engine：控制面唯一所有者 ├─ Scheduler / Capacity Planner / Benefit Policy ├─ KV Runtime / Block Manager / Swap Store ├─ Adaptive Prefill / Speculation └─ Iteration Transaction / Sequence State │ llama memory capability ├─ unsupported → upstream fallback └─ Attention KV → CUDA copy/COW/swap/remap

6.1 为什么强调“唯一所有者”

如果 HTTP、Scheduler、KV Manager 和 CUDA backend 都能直接修改 slot/KV 状态，就很难知道谁负责回滚、谁能释放资源。Engine 统一拥有控制状态，模块通过窄接口提供计划或机制，减少跨层隐式耦合。

6.2 prepare → plan → execute → commit/abort

  1. prepare：收集当前队列、slot、KV 容量和完成状态，建立本轮视图。
  2. plan：产生不可变的物理 batch/调度计划，不直接发布副作用。
  3. execute：调用真实 runtime/llama_decode，记录实际执行 token 数。
  4. commit：只有计划全部成功执行后才发布状态、推进位置和产生可见输出。
  5. abort：异常或部分执行时停止提交，保留失败原因并进行资源清理/重算。

它不是完整数据库 ACID：网络已经发出的字节无法回滚，也没有多节点隔离。但它保证单 iteration 内计划与运行时状态的原子可见性，并拒绝“只执行一半却提交整批”。

关键代码不变量：server_inference_iteration::begin_commit() 要求 executed_tokens == physical_batch_tokens；否则不能进入 committed。

6.3 为什么 Scheduler 只返回 plan

策略负责“应该做什么”，Runtime 负责“怎么做”。纯计划更容易单元测试、重放和比较；若 Scheduler 内直接搬 KV 或调用 CUDA，就无法在不启动模型的情况下验证公平性，也会把失败处理散到每个策略分支。

6.4 Capability fallback

不同 llama memory 类型并不都支持块级 Attention KV。调用方先询问 capability；不支持时保持上游行为。Fallback 是兼容性设计，不等于“所有模型都支持物理 paged KV”。

7. Scheduler、Aging 与容量规划

7.1 Decode 为什么通常优先

已经开始生成的请求每错过一轮，TPOT 都直接增加；而 Prefill 延迟主要进入 TTFT。Decode-first 能保护交互流畅度，但绝对优先会让新/长 Prefill 饥饿，所以必须加入 Aging、token budget 和 deadline。

7.2 Aging 防饥饿

Aging 随等待时间增加任务优先级。直觉上：

effective_priority = base_priority + α × waiting_time

α 太小无法防饿死，太大则刚等待一会儿的低价值任务抢占 Decode。项目强调不变量：长期等待的可运行任务最终应获得机会，而不是追求某个公式的理论最优。

7.3 缓存感知效用

utility ≈ reused_tokens − λ·victim_recompute_tokens + aging_bonus − deadline_risk

只最大化 prefix hit 可能为了复用 100 token 淘汰一个未来要重算 2000 token 的 slot。容量规划必须把回收收益、重算代价、deadline 和等待纳入。

7.4 为什么不用全局最优

未来到达时间、生成长度、回访概率不可知；精确组合优化在每 token iteration 中也过于昂贵。当前使用可解释启发式，并通过 upstream/fixed 模式、指标和实验控制风险。面试时不要声称求得全局最优。

7.5 Admission、Reservation 与 Victim

  • Admission：决定请求是否能进入当前容量。
  • Reservation：在执行前预留计划所需块，防止半途 OOM。
  • Victim：容量不足时选择可抢占对象；价值不仅是占用大小，还包括重算成本和活跃状态。

容量守恒可写为：free + allocated + reserved = capacity。任何失败路径都不能让同一块既 free 又被引用，或 reservation 永久泄漏。

8. Block Table、Prefix Sharing、COW 与 Swap

8.1 “Paged KV”在本项目里是什么意思

把连续 token 空间切成固定大小的逻辑 block，每条 sequence 的 Block Table 将逻辑块号映射到物理块 ID。类似操作系统页表，但只是类比：这里没有 CPU MMU 自动地址翻译，映射由软件显式维护。

学术参照：PagedAttention / vLLM, SOSP 2023。本项目仅借鉴块映射思想，未实现其 Attention kernel。

Sequence A logical: [0][1][2] │ │ └── physical 9 (private tail) │ └───── physical 5 (shared) └──────── physical 2 (shared) Sequence B logical: [0][1][2] │ │ └── physical 11 (private tail) │ └───── physical 5 └──────── physical 2

8.2 PrefixIndex 为什么不是普通字符串缓存

PrefixIndex 按 token block 的链式 hash 查找 exact prefix，并校验父块链和 token 内容。只用单块 hash 会把“同一 token 块但前文不同”的路径混在一起；只信 hash 又有碰撞风险。索引必须只发布已经写完、可共享的 canonical block。

8.3 Refcount 不变量

  • 每条 Block Table 引用贡献一次 refcount。
  • PrefixIndex 若拥有独立生命周期，也必须明确是否贡献引用。
  • refcount 归零且无 reservation/异步 lease 时才可回收。
  • 释放 sequence 时逐块递减，不能重复释放。

8.4 为什么 partial-tail 必须 COW

只共享完整 block 会浪费公共 prompt 尾部的 1…B−1 token。共享部分尾块能提高命中，但第一次 append 若原地写入会污染其他 sequence。因此写前检查共享状态：

  1. 发现 tail 的 refcount > 1；
  2. 预留/分配新物理块；
  3. 复制旧 tail 的有效 token；
  4. 复制成功后切换写者 Block Table；
  5. 再递减旧块引用；
  6. 任一步失败都保留旧映射。

复制复杂度由 whole-sequence 的 O(L) 降为 O(B)。这不是“零复制”：COW 在首次写时仍复制一个 tail block。

8.5 COW 与数据库事务的共同点

两者都遵守“先准备新状态，成功后原子发布，再回收旧状态”。区别是数据库事务还涉及并发隔离和持久性，而这里主要保证内存映射和异步复制的一致性。

8.6 Preemption 与 Swap

Preemption 把 GPU KV 让给更有价值的请求。可选择 recompute（释放后以后重算）或 swap（保存到 Host/File，稍后恢复）。Swap 适合重算成本高且 Host/磁盘传输可接受的序列；否则保存/恢复开销可能比重算更差。

阶段成功语义失败语义
save完整 payload+checksum 可见后才释放 resident KV保留 resident，不丢请求
file committemporary → flush/fsync → atomic replace旧文件仍有效，临时文件不可见
restore校验后完整安装状态和映射丢弃无效快照，完整 recompute
CUDA copyEvent 完成后才发布/复用 buffer不上报成功，不释放仍在用的资源

Swap payload 不能只有 K/V bytes，还需与 llama sequence 的逻辑状态兼容，否则恢复后位置、旋转或模型内部状态可能不一致。

9. CUDA：从零到真实 KV Remap

9.1 CPU、GPU、SM、Warp、Thread

CPU 擅长低延迟控制流，GPU 擅长大量相似工作。CUDA kernel 是在 GPU 上执行的函数；grid 由多个 block 构成，block 由多个 thread 构成。NVIDIA GPU 通常以 32 个 thread 的 warp 为调度单位。warp 内严重分支会让不同路径串行执行，称为 divergence。

官方依据：CUDA C Programming Guide。

9.2 内存层次与合并访存

  • Global memory：容量大、延迟高，KV tensor 位于此处。
  • Shared memory：block 内共享、片上、容量小。
  • Register：每 thread 私有、最快但过多会降低 occupancy。
  • Pinned host memory：不可分页的 Host 内存，便于 DMA/异步传输，但应受预算限制。

Coalescing 指相邻线程访问相邻地址，使硬件合并内存事务。128-bit 向量访问能减少指令和线程工作单元，但前提是地址和布局适合；它不自动提升带宽上限。

9.3 Remap descriptor

struct llama_kv_remap_copy {
    const uint16_t * source;
    uint16_t * destination;
    size_t staging_offset;
    size_t elements;
};

每个 descriptor 描述一段 FP16 元素的源、目的、staging 偏移和长度。公开 seam 同时支持 scalar 与 vectorized 模式，方便正确性对照和微基准。

9.4 为什么要 Gather → staging → Scatter

若映射重叠或循环，例如 A→B、B→A，直接依次复制会让第一次写覆盖第二次尚未读取的源。Gather 先把所有源读入独立 staging，形成同一时刻的 snapshot；Scatter 再统一写回，从而保证顺序无关。

错误：A → B（B 被覆盖）→ A（读到新 B） 正确：A,B → staging[A,B] → B,A

完全不重叠映射不需要 snapshot，多个 cudaMemcpyAsync 可能比两次 kernel 加 staging 更快，所以正确的生产策略应分流，而不是“所有复制都 kernel 化”。

9.5 为什么 uint4 是 128 bit

CUDA 的 uint4 包含 4 个 32-bit unsigned integer，总计 16 byte = 128 bit。KV 元素是 FP16（2 byte），因此一次向量工作单元覆盖 8 个 FP16。代码不是把 FP16 做整数计算，而是用等宽类型搬运原始 bit。

9.6 对齐与尾部

source、destination、staging 都满足 16-byte 对齐且剩余至少 8 个 FP16 时才可安全走完整向量路径。地址不对齐或最后不足 8 个元素时逐元素回退。守卫区测试验证 kernel 没写到合法范围之外。

9.7 Launch geometry 与溢出

work = ceil(max_elements / elements_per_work)
grid_x = ceil(work / 256)

实现用商加余数的方式 ceil-div，避免 max_elements + 7 在 size_t::max 附近溢出；Host 在 launch 前检查 grid.x ≤ 2³¹−1、grid.y ≤ 65535。这属于输入验证，不应等 CUDA runtime 模糊报错。

9.8 Stream、Event 与异步错误

把 kernel 放入 stream 只表示入队，不表示 GPU 已完成。Event 记录在 stream 中，cudaEventSynchronize 建立 Host 等待点；在它成功前，descriptor、staging、source/destination lease 都不能释放。Kernel launch 错误可由 cudaGetLastError 发现，执行期错误常要到同步点才暴露。

审查后修复：Remap byte、kernel launch、COW 和 copied block 指标只在 Event 同步成功后累加，避免失败操作污染 Prometheus 证据。

9.9 Compute Sanitizer 能证明什么

  • memcheck：检测非法/越界访问和部分 API 错误。
  • racecheck：检查 shared-memory 数据竞争等 hazard。
  • 不能证明：所有输入都正确、没有逻辑 bug、性能好、没有未覆盖的竞态、不同 GPU 都安全。

本项目新 Remap 的 memcheck 0 error、racecheck 0 hazard；还需 CPU oracle、边界/尾部测试和真实 Qwen 输出对照共同建立信心。

10. 在线 Ridge、置信度与保守收益门控

10.1 为什么需要在线门控

同一种 CacheFlow 策略在 CPU 和 CUDA、短/长上下文、低/高并发下可能方向相反。固定阈值无法覆盖硬件与负载变化，因此控制器为 upstream 与 CacheFlow 分别学习成本，并只在证据足够时启用。

10.2 Ridge Regression

设特征向量 x 包含 backend、上下文 bucket、并发、prefix reuse、KV 压力等，目标 y 是观测成本。Ridge 目标：

minθ Σ(yi−xiTθ)² + λ||θ||²
A = λI + ΣxixiT, b = Σxiyi, θ = A−1b

λ 是 L2 正则：过小会让少量/共线样本导致系数不稳定，过大会把系数压向零、产生欠拟合。在线更新只需累加 A 和 b，不必保存所有历史样本。

置信探索参照：LinUCB, WWW 2010。项目是服务成本门控，不是新闻推荐算法复现。

10.3 不确定性半径

prediction = xTθ
radius ∝ β·σ·√(xTA−1x)

xᵀA⁻¹x 是当前方向的数据稀缺程度：训练样本充分覆盖该方向时 A 的信息量大，逆矩阵方向值小；陌生 workload 则半径大。β 越大越保守。

10.4 Positive lower bound

定义预测收益为 upstream cost − CacheFlow cost。只有：

predicted_benefit − uncertainty − safety_margin > 0

才因为 positive_lower_bound 启用 CacheFlow。预测均值为正但下界不正，仍应走 upstream。这是“宁可错过收益，也减少错误启用”的保守策略。

10.5 冷启动、有限探索、漂移与 cooldown

  • Cold start：样本不足时 fail closed，默认 upstream。
  • Safe exploration：风险可接受且满足间隔时有限尝试 CacheFlow，用于收集反事实动作数据。
  • Drift：实际残差持续远超历史尺度，说明分布变化。
  • Cooldown：漂移/SLO 风险后暂时退回 upstream，防止反复抖动。

探索是为了学习，不等于模型已有正收益证据；指标必须分开记录 safe_exploration 与 positive_lower_bound。

10.6 为什么按 backend 分模型

CPU 的计算/内存比例、CUDA 的 kernel launch/batching/WDDM 抖动不同。把两者混在一个线性模型里，会用 CPU 的收益证据错误启用 CUDA。项目维护 backend-local state，并把 compatibility key 绑定模型与 serving shape。

10.7 Checkpoint 为什么属于算法正确性

若在线模型重启即丢失，它会重复探索，发布/故障恢复会改变决策行为。Checkpoint 保存 A、b、残差、cooldown 和探索进度；恢复前校验 schema、feature count、兼容 key、CRC、矩阵维数/对称性和有限数值，全部通过后一次性替换状态。损坏文件 fail closed 到空模型。

11. Adaptive Prefill 与 Speculation

11.1 Adaptive Prefill

动作是 chunk size。控制器按 backend/context/concurrency bucket 记录候选成本，在 greedy、固定候选与在线估计之间选择。它的价值不一定是击败所有固定点，更现实的是识别并规避明显坏点。

Chunk优势风险
小更快让出 GPU 给 Decode更多调度、launch、iteration 开销
大大矩阵利用率/吞吐较好Head-of-line blocking，TPOT/TTFT 尾部恶化

11.2 Speculative Decoding 基础

标准推测解码用便宜 draft model 提议多个 token，再由 target model 一次验证；通过接受/拒绝规则保持目标分布。加速来自减少昂贵 target model 的串行步数，而不是“跳过正确性验证”。

原始算法：Fast Inference from Transformers via Speculative Decoding, ICML 2023。

11.3 本项目的边界

项目采用 N-gram 候选和 adaptive draft length，控制器依据接受率 EWMA、最小证据、迟滞和 KV 压力调整深度。它不是论文中的完整 draft-model speculative decoding，不能写成“复现全部推测解码算法”。

深度过大时无效 draft 计算和 KV 临时状态增加；过小时即使接受率高也难摊薄验证开销。EWMA：

mt = α·observationt + (1−α)·mt−1

α 大响应快但噪声大，α 小稳定但跟不上分布变化；迟滞用不同升/降阈值减少来回切换。

12. 实验设计、证据等级与负结果

12.1 证据金字塔

  1. 代码存在：只能证明写过。
  2. 单元测试：证明选定输入上的算法/不变量。
  3. Sanitizer：提高内存/竞态信心。
  4. 真实模型 smoke：证明进入真实路径并保持输出/协议。
  5. 微基准：隔离回答某个机制的成本。
  6. 端到端配对实验：回答用户指标，但受混杂影响更大。
  7. 跨模型/硬件/长期线上：才接近外部有效性；本项目尚未达到。

12.2 Paired trial 与 Latin rotation

配对实验在相同 trial 环境比较 A/B，先算每对差异，再对差异做统计，能抵消温度、后台负载等共同漂移。交替/Latin rotation 改变执行顺序，减少永远“先跑 A、后跑 B”的热机偏差。

paired improvementi = (scalari − vectori) / scalari

median(A)/median(B) 不是 median paired ratio；前者可能来自不同 trial。中位数抗离群，但不能替代置信区间或足够样本。

12.5 为什么 Full 没稳定全绿

2026-08-01 的基线版本曾完整通过 Full；新增 Remap 后两次重跑分别在既有统计门禁失败：

  • 一次长驻末态预测收益 7.86 ms，小于不确定性 9.00 ms；同场景单独复现为 17.82 ms > 8.49 ms。
  • 另一次 CPU learned oracle regret 26.1% 超过 20%，CUDA paired regression 3.7% 超过 3%。

失败点不同且专项功能稳定，说明统计实验受 WDDM、调度、温度和执行时序影响；但不能因此宣布 Full 通过。正确表述是“增量专项门禁通过，全量统计门禁仍需更稳健的样本量、收敛窗口和置信区间设计”。不要无限重跑直到抽到绿灯，也不要悄悄放宽阈值。

12.6 因果链怎么讲

策略干预（upstream vs CacheFlow） → 决策计数改变 → Scheduler mediator（chunk/token/batch）改变 → CUDA mediator（kernel/bytes/event）改变 → Engine phase 时间改变 → TTFT/TPOT/吞吐结果改变

每一箭头都要有观测，否则只是相关性故事。此前 paired profiling 中强制 CacheFlow 确实改变 scheduler 和 CUDA mediator，但 TTFT P95 反而恶化；这是说明控制策略与 GPU batching 交互的负结果，不是项目失败，也不能被省略。

12.7 常见混杂因素

  • GPU dynamic clock、温度、功耗限制和 WDDM；
  • 模型/文件系统缓存、首次初始化；
  • 执行顺序、进程复用、后台程序；
  • 不同输出长度、EOS、batch composition；
  • 近似相等 logits 因浮点归约顺序改变而产生 token 差异；
  • 只看均值掩盖尾延迟。

15.2 Transformer 与模型基础

P0为什么 Attention 要分 Q/K/V？

同一隐状态通过不同线性投影承担查询、匹配索引和值的角色，使模型能按当前位置需求选择历史信息。若共用同一表示，表达能力和角色分离受限。

P0为什么除以 √d？

若各维近似独立同方差，点积方差随 d 增长。除以 √d 让尺度更稳定，避免 softmax 进入极端饱和区导致梯度/概率过尖。

P0KV Cache 缓存的是什么，为什么不缓存 Q？

缓存每层历史 token 的 K/V。新 token 的 Q 只在当前步查询历史，之后不再被未来位置直接读取；未来位置需要历史的 K/V，因此它们值得保存。

P0Prefill 和 Decode 有什么区别？

Prefill 处理多个 prompt token，矩阵较大、主要影响 TTFT；Decode 每序列每轮通常一个 token，算子窄且反复读取 KV，主要影响 TPOT，往往更 memory/launch sensitive。

P1GQA 为什么省显存？

KV 容量取决于 KV head 数。GQA 让多组 Q head 共用较少 K/V head，因此相对 MHA 按 Hkv/H 比例减少 KV 和读带宽。

P1RoPE 对 KV Cache 有什么影响？

RoPE 通常在写 K 前根据位置旋转；恢复或移动 KV 必须保持位置/sequence state 一致。不能只拷贝 bytes 却丢失逻辑位置状态。

P1量化权重是否意味着 KV 也是 4 bit？

不一定。模型文件 Q4_K_M 描述权重量化；KV dtype 是独立配置/实现选择。本项目 Remap 和容量示例按 FP16 KV，不能用权重 bit 直接代入 KV 公式。

P2为什么 batch composition 可能改变输出 hash？

浮点运算不满足严格结合律，不同 batch/归约顺序可能让近似相等 logits 的排序或 EOS 位置变化。协议、确定 seed 和语义质量应分别验证，不能要求所有并发布局逐字节一致。

15.3 Serving 与 Scheduler

P0什么是 Continuous Batching？

在每个生成 iteration 边界动态加入新 sequence、移除完成 sequence，而不是固定整批直到所有请求结束。它减少空洞并提高 GPU 利用率。

P0为什么 Decode 优先但又要 Aging？

Decode 延迟一轮直接恶化 TPOT，所以通常优先；绝对优先会让长 Prefill 永远进不来，Aging 让等待时间转化为优先级，保证最终服务。

P0TTFT、TPOT、吞吐如何权衡？

大 batch/chunk 提高吞吐但可能阻塞首 token和 Decode；小 chunk改善交互但增加 launch/调度开销。应同时报告 TTFT/TPOT/latency/throughput 的中位与尾部，而非单指标优化。

P1缓存感知调度为什么不能只看最长公共前缀？

复用收益可能小于淘汰其他 slot 的重算代价，还受 deadline、等待和容量约束。效用应是 reuse、victim cost、aging 和风险的组合。

P1Scheduler 复杂度如何？

小 slot 集合下候选扫描约 O(S)；Prefix 按 block 递进约 O(P/B)，具体还取决于 hash bucket 验证。项目选择低开销可解释启发式，不做昂贵全局优化。

P1背压为什么比扩容队列更重要？

无限队列只把过载转化为内存增长和不可控尾延迟。背压让过载显式失败，保护在途请求和服务恢复能力；应用用并发槽与 429 验证。

P2如何避免 Scheduler 自己成为瓶颈？

保持 per-iteration 计算近线性/小常数、纯 plan、增量索引和预计算 bucket；用 Engine trace 比较 plan 占比。若 slot 数扩大会考虑 heap/分层队列，但需衡量更新成本。

15.4 KV、COW 与 Swap

P0Block Table 类比页表有哪些相同和不同？

相同：逻辑空间映射到离散物理块，降低连续分配与碎片压力。不同：没有硬件 MMU/TLB 自动翻译，由 serving/runtime 显式维护，block 大小和语义也针对 token/KV。

P0为什么共享 partial tail？

只共享完整块会丢失最多 B−1 个公共 token 的复用。共享 tail 提升命中，但 append 前必须 COW。

P0COW 正确操作顺序？

分配新块→复制有效 tail→复制成功后切换当前 sequence 映射→递减旧引用。失败前不修改旧映射，保证其他共享者和写者都安全。

P1如何证明 refcount 正确？

定义 Block Table/索引/异步 lease 对引用的贡献，验证 refcount 等于所有活跃引用之和；随机状态测试执行 attach/append/release/COW 后检查容量和父链不变量；真实 smoke 验证路径。

P1Prefix hash 碰撞怎么办？

Hash 用于缩小候选，不能作为最终相等证明；还需校验父链、token 数量和实际 token 内容。否则错误共享会直接破坏模型输出。

P1Swap 还是 recompute，怎么选？

比较保存+恢复传输/存储成本与未来重算 Prefill 成本，并考虑回访概率、Host budget 和 deadline。短/低价值序列可能直接 recompute 更好。

P1为什么 file swap 要临时文件+原子替换？

直接覆盖若中途失败会破坏旧快照。先完整写临时文件并 flush/fsync，再 atomic replace，使读者看到旧完整版本或新完整版本，而非半写文件。

P2ABA/并发释放如何防？

用唯一 block/operation generation、明确所有权和 event lease，避免物理 ID 回收后旧异步回调误认为仍是同一对象。当前单机控制面简化并发，但异步 CUDA 生命周期仍需独立 lease。

15.5 CUDA 与算子

P0这个 CUDA 算子具体做什么？

它按 descriptor 把真实 K/V tensor 的若干 source range Gather 到 staging，再 Scatter 到 destination；用于跨 stream/block Remap 和需要 snapshot 的 COW/映射复制，不计算 Attention。

P0为什么用 staging？

重叠/循环映射中直接 in-place copy 会覆盖尚未读取的源。两阶段先建立完整快照，再写回，保证与 descriptor 执行顺序无关。

P0uint4 为什么能加速？

每 thread 从处理 1 个 FP16 变为最多 8 个，减少线程和 load/store 指令固定开销，并形成 16-byte 访问。大规模时受内存带宽限制，收益会收敛。

P0非对齐怎么办？

运行时检查 source/staging 或 destination/staging 的 16-byte 对齐；不满足或尾部不足 8 元素时在同一 kernel 标量逐元素处理，保证正确性优先。

P1为什么不全部用 cudaMemcpyAsync？

不重叠的连续 range 用 memcpy 往往更快；重叠/循环映射需要全局 snapshot，单纯异步 memcpy 的顺序语义不够。生产路径应按 mapping 性质分流。

P1kernel 返回成功为什么还可能失败？

Launch 是异步入队，cudaGetLastError 主要捕获 launch 配置等错误；非法内存访问可能到 Event/Device 同步才暴露。因此指标和资源释放必须等同步成功。

P1为什么小 block 收益大、大 block 收益小？

小工作量中线程/指令/launch 固定开销占比高，向量化减少它们；大工作量中 global memory bandwidth 主导，标量线程也能形成较好合并访问，剩余优化空间小。

P1怎么验证 snapshot 语义？

构造 A↔B 重叠交换，先在 CPU 对原始数组做独立快照得到 oracle，再运行 GPU Gather/Scatter 对比完整数组；不能用同一 GPU 实现生成期望值。

P1Sanitizer 0 error 是否等于无 bug？

不是。它只覆盖本次运行和工具能检测的错误；仍需边界输入、逻辑 oracle、真实模型输出和不同设备验证。

P2下一步为什么是 Paged Decode Attention？

当前先 Remap 再让 Attention 读取连续 KV，仍有搬运。Paged Attention 让 kernel 通过 Block Table 直接读取非连续 KV，可能消除部分 copy。应先支持受限 Qwen GQA/FP16/decode，保留上游回退并验证数值与端到端指标。

15.6 在线学习与实验

P0为什么用 Ridge 而不是神经网络？

特征维度小、在线样本有限，需要低开销、可解释、可增量更新和置信度估计。复杂模型会增加冷启动、过拟合和每 iteration 成本。

P0正则 λ 的作用？

让 A 可逆并抑制系数过大，降低共线/少样本的不稳定。太大欠拟合，太小高方差。

P0为什么只在 lower bound 正时启用？

均值正不能排除估计误差；下界减去不确定性和安全 margin 后仍为正，才有更保守的收益证据，降低错误启用有害策略。

P1不探索怎么学 CacheFlow 成本？

需要 bounded safe exploration 收集另一动作样本，但应限制频率、风险和冷却；长期实验与短进程风险预算分开。探索决策不能冒充正下界利用。

P1为什么 Full 会波动？

性能门槛接近噪声尺度，受 WDDM、GPU clock/温度、调度和样本量影响；一次 terminal snapshot 也可能不稳。应增加样本、预注册统计、使用置信区间与 bounded convergence，而不是重跑挑好结果。

P1微基准与端到端冲突怎么办？

不冲突：kernel 局部更快，但在总请求中占比小，或改变 batching/launch 数、引入控制成本。用 Amdahl 定律和因果链定位；不能从局部 53% 推出服务 53%。

P1为什么配对实验优于独立中位数？

同一 trial 的环境漂移对 A/B 更相似，先做差可抵消公共噪声。独立中位数可能来自不同热状态，比例不对应任何真实 pair。

P2如何给 Remap 改善加置信区间？

对 20 个 paired improvement 做 bootstrap 重采样，计算中位改善的 percentile/BCa 区间；预先规定重采样次数和判定阈值。若区间跨 0，只能说趋势而非稳定提升。

15.7 系统、数据库与工程延伸

P0RAII 在这里有什么价值？

把 stream/event/buffer/file handle 生命周期绑定对象析构，异常或早退时自动清理，减少 goto/多分支泄漏。异步资源还要确保析构前 work 已完成，RAII 不自动解决 happens-before。

P1Counter、Gauge、Histogram 怎么选？

累计决策/byte 用只增 Counter；当前 cooldown/预测值用 Gauge；TTFT/TPOT 分布用 Histogram。失败操作不能累加成功 Counter。

P1SQLite 为什么每操作新连接？

线程式 HTTP 服务中避免跨线程长期共享连接及泄漏，操作边界清晰。代价是连接开销；当前本地低并发可接受，更高吞吐可用连接池和 WAL。

P1取消为何可能留下半状态？

网络断开、模型 generator、KV slot 和数据库是不同资源。必须沿层级传播关闭；数据库只在完整生成后写 assistant，并在同一事务更新 session。

P2如果扩展多 GPU，最大的变化？

要引入 tensor/pipeline parallel、跨设备 KV placement/通信、拓扑感知调度、分布式状态/故障模型。当前单机 refcount 和 atomic file 语义不能直接外推。

16. 白板推导与现场编码

16.1 必会推导一：KV 容量

  1. 每层每 token 有 K/V 两份；
  2. 每份含 Hkv×Dhead 个元素；
  3. 乘元素 byte、层数、token、sequence；
  4. 最后换算 KiB/MiB/GiB，说明不含权重和 workspace。

面试官改变 MHA→GQA、FP16→FP8、并发或 context 时，应能即时按比例缩放。

16.2 必会推导二：Ridge 正规方程

J(θ)=(y−Xθ)T(y−Xθ)+λθTθ
∇J=−2XTy+2XTXθ+2λθ=0
(XTX+λI)θ=XTy

再把历史和写成在线 A、b。不要机械背导数：解释 λI 让矩阵更稳定、A 表示累计信息。

16.3 必会推导三：COW 状态机

ensure_writable(sequence):
    tail = table.last()
    if tail.refcount == 1: return tail
    reserve 1 block
    fresh = allocate()
    copy(valid_prefix(tail), fresh)
    wait/verify copy success
    table.replace_last(fresh)   // publish
    decref(tail)               // retire old
    return fresh

追问失败处理：allocate/copy/wait 任一失败都不能 replace/decref；reservation 要释放；旧 tail 仍可读。

16.4 必会编码一：安全 ceil-div

size_t ceil_div(size_t n, size_t d) {
    return n / d + (n % d != 0); // 避免 (n + d - 1) 溢出
}

进一步检查 d != 0，结果是否超出 CUDA grid 上限，类型转换是否截断。

16.5 必会编码二：一维 CUDA kernel

__global__ void copy(const half *src, half *dst, size_t n) {
    size_t i = (size_t)blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) dst[i] = src[i];
}

追问：为什么转 size_t？如何算 grid？为什么仍需同步检查？如何变成 8-element vector path？

16.6 Amdahl 定律解释局部优化

overall speedup = 1 / ((1−p) + p/s)

若 Remap 只占端到端 2%，即使局部加速 2 倍，总加速也约 1.01 倍。因此要测其占比、调用次数和对 batching 的副作用。

16.7 现场系统设计题：增加 Paged Decode Attention

  1. Scope：先支持 Qwen2.5、FP16 KV、GQA、single-token decode、单 GPU。
  2. 接口：Q、Block Table、KV block pool、sequence length、head mapping → output。
  3. 算法：按 KV block 流式计算 score，在线维护 max/sum 做稳定 softmax，避免存完整 score。
  4. 正确性：与上游连续 Attention 对照误差，覆盖非整块 tail、共享 Prefix、不同长度。
  5. Fallback：不支持 dtype/layout/head dim 时回上游。
  6. 性能：先 kernel microbench，再证明 KV copy byte 减少，最后测 Decode TPOT/TPS。
  7. 边界：不声称通用 vLLM PagedAttention，不先支持 Prefill、多 GPU、全部量化。
