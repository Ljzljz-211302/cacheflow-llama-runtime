开场会出现的核心词：零基础先读这里

Prefix 是多条请求相同的输入前缀；Remap 是按映射把 KV 从一组物理块搬到另一组；Paged 是通过页表直接访问不连续物理页；Direct 是布局兼容时直接复用；Swap 是把 KV 暂存到其他设备或主机；Recompute 是丢弃后重新计算。CUDA 是 NVIDIA 的 GPU 并行编程平台；kernel 是提交给 GPU 并行执行的函数；CUDA event 是插入 GPU 命令流的计时/依赖标记。

Descriptor 是描述源块、目标块和长度的小结构体；Gather/Scatter 分别表示把分散数据收集到 staging、再分发到目标；aligned 表示地址和长度满足特定字节对齐。FP32 是 32-bit 浮点；online softmax 是不保存全部分数、逐项更新最大值/分母/加权和的 softmax。L2 正则是在拟合误差之外惩罚过大参数；bootstrap 是对原样本有放回重采样来估计不确定性；P99 是 99% 观测不超过的分位数。后文会逐一推导这些概念，而不是只给一句定义。

CPU 是负责通用串行控制的中央处理器；NSYS 是 Nsight Systems 的简称，用于观察 CPU/CUDA 时间线；COW 是 Copy-on-Write（写时复制），共享数据在写入前先复制。Prometheus 的 Counter 是单调累计量，Gauge 是可增可减的当前值，Histogram 是按区间桶累计的分布；它们在后文都有项目实例。

0. 先看懂整条故事：这个项目为什么会长成现在这样

0.1 不从模块名开始，从一个真实服务场景开始

设想实验室部署了一台只有一块 RTX 4050 Laptop GPU 的问答服务。用户 A 发送“你是东北大学推免面试官……”加上一段长材料；几乎同时，用户 B 使用同一段系统提示词，只替换了最后一个问题；用户 C 已经拿到首 token，正在等待后续回答。此时显存接近上限，又到来用户 D。

如果把每个请求从头到尾独占执行，C 的每个新 token 都要等 A、B 的长输入处理完，交互会卡顿；如果让所有请求同时进入，又可能没有足够显存保存它们的历史状态。A 与 B 的公共前缀重复计算很浪费，但直接共享缓存后，任何一方继续写入又可能污染另一方。即使逻辑上决定“搬一块缓存”，GPU 上仍要面对不连续地址、重叠复制、异步执行和错误回滚。最后，即便某个 CUDA kernel 在小数据上更快，也不代表服务端应该永远选它。

CacheFlow Runtime 的故事，就是依次解决下面六个冲突：

冲突 1：谁先运行？长 Prefill 会阻塞正在 Decode 的请求。→ Engine + Scheduler
冲突 2：历史状态放哪？KV Cache 随上下文和并发线性增长，连续显存难找。→ KV Block Runtime
冲突 3：公共前缀怎样安全复用？共享能省计算，但共享尾块不能被原地写坏。→ Prefix Index + refcount + COW
冲突 4：物理数据怎样真正搬？映射可能碎片、重叠、错位，而且 GPU 调用是异步的。→ CUDA Remap / Swap
冲突 5：能否不搬就直接算？先整理 KV 再 Attention 会多一次显存读写。→ Paged Decode Attention
冲突 6：不同场景到底选哪条路？Direct、Remap、Paged、Swap、Recompute 的胜负随状态变化。→ Gate + Cost Model + Benefit Policy

0.2 一条请求经过系统时，每个模块具体接了哪一棒

① HTTP 层收到 A/B/C/D，建立 request 与取消、deadline 信息 ↓ ② Scheduler 只选择“下一轮”要运行的 sequence：C 的 decode 优先，A/B prefill 切块 ↓ ③ KV Block Manager 估算本轮需要多少块；不够时给出淘汰、Swap 或 Recompute 候选 ↓ ④ Prefix Index 发现 B 与 A 有公共 token 前缀，让 B 的 Block Table 指向已有物理块 ↓ ⑤ B 要在共享尾块后追加 token：COW 先复制尾块，再把 B 的映射切到新块 ↓ ⑥ Action Policy 先排除不合法动作，再估计 Direct/Remap/Paged/Swap/Recompute 成本 ↓ ⑦ CUDA Backend 根据计划执行向量化 Remap、异步 Swap，或让 Paged Attention 直接查页表 ↓ ⑧ llama_decode 完成一次模型计算；Engine 只有成功后才 commit 新映射与 sequence 状态 ↓ ⑨ SSE 向用户推送 token；Prometheus、trace 与实验制品记录“做了什么、花了多久、结果怎样”

这条链有两个控制方向：请求和 KV 数据从上往下流；完成事件、错误、容量与耗时从下往上反馈。调度器不能绕过 Block Manager 随便承诺显存，Block Manager 也不能绕过 CUDA 完成事件提前发布映射。模块划分的真正依据不是文件类型，而是状态所有权与失败边界。

0.4 为什么不是把所有功能写在一个大循环里

上游推理服务的大循环可以“能跑”，但当调度、缓存映射、CUDA 生命周期和网络输出都修改同一批状态时，一次 OOM 或异步错误会留下难以判断的半完成状态。项目重构的核心贡献不是把函数拆小，而是建立所有权：

  • Scheduler 拥有选择权，但只输出计划，不能直接改物理映射。
  • Block Manager 拥有块与引用计数，是容量账本的唯一真相来源。
  • CUDA Adapter 拥有异步资源租约，event 完成前不能释放 source、destination、staging 或 pinned buffer。
  • Engine 拥有提交权，execute 成功才把 shadow plan 变成对外可见状态。
  • Evidence System 不参与决策，但记录可关联 ID，使每个结论能回到原始请求和 GPU 操作。
贯穿全手册的判断方法：看到一个类或算法时，先问“它拥有哪份状态、输入和输出是什么、失败后由谁恢复”，再学习公式和实现。答清这三问，模块就不再是孤立名词。

1.1 30 秒版本

我基于固定版本的 llama.cpp 深度重构了单机大模型推理服务 CacheFlow Runtime。核心工作有三层：系统层实现迭代级调度、分页 KV、Prefix 共享、写时复制和换出恢复；GPU 层使用 CUDA（NVIDIA 的 GPU 并行编程平台）实现 128-bit KV Remap 与受限 Paged Decode Attention 算子；算法层设计统一的 Direct、Remap、Paged、Swap、Recompute 动作接口，用在线 Ridge 回归（带 L2 正则、可抑制小样本极端系数的线性回归）和置信下界保守选择。项目不是只跑通功能：我用真实 Qwen2.5、Prometheus（用于采集 Counter/Gauge/Histogram 的监控系统）、Nsight Systems（CPU/CUDA 系统时间线分析器）、配对 bootstrap 重采样和哈希绑定制品建立了可复核证据。Remap 在 aligned 1-block 场景 CUDA-event 中位改善 57.10%，线上决策路径 P99 最坏 5 微秒，真实应用累计触发 560 万字节向量化搬运。

1.2 3 分钟版本：按“问题—设计—实现—证据”说

问题：自回归大模型每生成一个 token 都要读取历史 Key/Value。并发请求增加后，KV Cache 成为主要动态状态：它会产生碎片、共享前缀、写冲突、显存压力和数据搬运。单一固定策略无法同时适应短上下文、长上下文、连续布局和碎片布局。

系统设计：我把一次模型迭代拆成 prepare、plan、execute、commit。plan 只生成无副作用的计划；execute 执行模型与 KV 动作；commit 原子更新块表和请求状态，失败则回滚。逻辑块通过 Block Table 映射到物理块，多请求可共享公共 Prefix；共享尾块写入前执行 Copy-on-Write，也就是先复制再改映射，避免污染其他请求。

GPU 与模型算法：对 KV 搬运，我写了 descriptor-driven Gather/Scatter kernel，满足 16 字节对齐时每线程用 uint4 搬 128 bit，不对齐或有尾部时安全回退标量。进一步实现了受限 Paged Decode Attention：kernel 根据页表直接读取非连续 K/V，用 FP32 online softmax 单遍维护最大值、分母和加权 V，避免先把分页 KV 重排为连续缓存。

决策算法：我没有把“某个 kernel 在微基准更快”直接写死为生产规则，而是统一建模 Direct、Remap、Paged、device/host Swap 与 Recompute。先用 capability gate 排除不合法动作，再为每种动作维护独立的在线 Ridge 成本模型；只有候选的保守收益下界仍优于基线并超过 margin 才切换，否则 fail closed 回到安全动作。

证据：正确性覆盖 CPU FP32 oracle、跨页/碎片页、COW、故障回滚和 Compute Sanitizer。性能上区分无 profiler 主结果与 profiler 机制证据，使用成对、交替顺序和 bootstrap 区间。aligned 1-block Remap CUDA-event 改善 57.10%，并由 NSYS 证明 scalar/vector launch 都是 10/10，收益来自单次搬运路径而不是少发 kernel。统一 chooser 做了 500 万次调用，P99 1 微秒、零堆分配；短周期在线门控 CPU/CUDA paired-oracle regret 为 5.04%/10.52%，决策 P99 最坏 2/5 微秒。

2. 从零理解大模型推理

2.1 模型、token 与推理

模型是一组训练后固定的数值参数和计算规则；推理是拿这些参数处理新输入，不再更新参数。文本先由 tokenizer 切成整数编号，每个编号叫 token；token 不一定是完整汉字或单词。自回归生成的含义是：模型根据已有 token 预测下一个 token，把它追加到序列，再重复。

Prefill是一次并行处理整段输入 prompt，构造每层历史状态并产生首 token 所需状态；Decode是在已有状态上逐轮生成新 token。Prefill 通常更偏计算密集，Decode 每轮只增加一个位置，却要读取全部历史 KV，因此常受显存带宽和调度开销影响。

2.2 Transformer Attention 到底算什么

对当前层输入矩阵 X，三组权重得到 Query、Key、Value：

Q = XWq，K = XWk，V = XWv score = QKᵀ / √d P = softmax(score + causal_mask) output = PV

Query（查询）表示当前位置想寻找什么；Key（键）表示历史位置可按什么被匹配；Value（值）是匹配后实际聚合的内容。d 是每个头的维度，除以 √d 防止点积随维度增大而过大。softmax 把分数变成和为 1 的非负权重。causal mask（因果遮罩）禁止位置看到未来 token。

Decode 时历史 token 的 K/V 不会因新 token 改变，所以把它们缓存起来；当前 token 只需计算自己的 Q/K/V。这个缓存就是 KV Cache。它缓存的是每层每个历史 token 的 K 和 V，不是最终输出。

2.3 MHA、GQA 与本项目形状

MHA（Multi-Head Attention，多头注意力）让多个 Query head 学习不同关系。GQA（Grouped-Query Attention，分组查询注意力）让多个 Query head 共用一个 KV head，以降低 KV 容量和读取量。若 Query head 数为 Hq、KV head 数为 Hkv，组大小为 g=Hq/Hkv，第 qh 个 Query head 使用 kvh=floor(qh/g)。

真实 Qwen2.5-0.5B 为 24 层、14 个 Query head、2 个 KV head、head dimension 64，GQA 比为 7；研究中 7B-shape 为 28/4/128，也保持比 7。面试时必须区分真实模型形状与用于扩大计算规模的 synthetic shape。

2.4 KV 容量白板公式

KV bytes = 2 × L × T × Hkv × D × B

2 表示 K 和 V；L 是层数；T 是缓存 token 数；Hkv 是 KV head 数；D 是 head dimension；B 是每元素字节数。FP16 是 16-bit 浮点格式，每元素 2 bytes；FP32 是 32-bit 浮点格式，每元素 4 bytes、精度更高。例：24 层、1024 token、2 KV heads、D=64、FP16，需要 2×24×1024×2×64×2=12,582,912 bytes，约 12 MiB。并发序列和长上下文会线性放大该值。

2.5 服务指标不能混用

  • TTFT（Time To First Token）：请求到达至首个可见 token，包含排队、Prefill 和首轮执行。
  • TPOT/TBT（Time Per Output Token / Time Between Tokens）：首 token 后每个 token 的平均或相邻间隔。
  • 吞吐：单位时间完成的 token 或请求数；吞吐上升不保证单请求尾延迟下降。
  • P95：95% 样本不超过的值，关注尾部体验；它不是平均值。
  • CUDA-event time：GPU stream 中两个 event 之间的设备区间；不等于用户请求延迟。
  • SLO（Service Level Objective，服务等级目标）：系统预先承诺或内部规定的延迟、可用性等目标。
自测：为什么 kernel 快 50% 不能直接说 TTFT 快 50%？
答案TTFT 还包含排队、CPU 调度、Prefill、其他 kernel、数据传输和同步；目标 kernel 只占其中一部分，且策略变化还可能改变 batch 与 prefill 形状。

3.1 为什么是 iteration-level scheduling

iteration-level scheduling（迭代级调度）不是一个请求占住 GPU 直到生成完，而是每轮只决定下一次模型迭代的 batch。这样新请求可以加入，完成或取消的请求可以离开，长 Prefill 可切成 chunk 与 Decode 交错。它也叫 continuous batching，因为 batch 的成员会在迭代之间连续变化。

调度器需要同时处理容量、deadline、公平性和吞吐。Aging 是“等待越久优先级越高”的机制，避免短请求不断插队导致长请求饥饿。Backpressure 是容量不足时明确拒绝或延迟接入，而不是继续堆积直至内存崩溃。

3.2 prepare/plan/execute/commit 为什么像数据库事务

  • prepare读取当前状态并校验资源。
  • plan生成本轮动作，但不修改正式 Block Table。
  • execute执行模型、拷贝或 swap，可能失败。
  • commit仅在 execute 成功后一次性公开新映射；失败丢弃 shadow state。

这提供映射层的失败原子性：一次迭代不会发布半完成的新 Block Table 映射。执行失败时仍会记录失败指标/学习观测、释放 slot，并可保守清空受影响序列的 prompt/context 后走 Recompute；“原子”不等于所有可观察计数完全不变。它解决的核心是避免 refcount 已减但新块尚未就绪的半提交映射。

3.3 Engine trace 说明什么

一次 CPU mixed workload 记录 242 个完整 span，总时长 9.553 秒：execute 占 99.9145%，commit 0.0674%，plan 0.0148%，prepare 0.0033%。Span 是带开始与结束时间的阶段记录。这个结果说明控制面的事务分层开销很小，主要时间仍在模型执行；它不是采样调用栈火焰图，不能据此推断某个 CPU 函数的周期占比。

3.4 Batch、sequence 与 token batch 不是同一个概念

sequence（序列）是一条独立生成状态，例如一个用户的一次对话；它拥有自己的历史 token、KV Cache、结束状态和取消状态。token batch是某一轮送进模型的 token 集合，它可能同时包含多个 sequence 的 Decode token，也可能包含某个长 Prompt 的多个 Prefill token。面试中说“batch=8”必须进一步说明：是 8 条 sequence、8 个 token，还是内部 micro-batch 上限，否则结论不可复现。

概念回答的问题典型变化
并发请求数系统里同时有多少用户请求？受接入、排队和完成影响
active sequence 数多少条生成状态仍占用 KV？请求完成、取消或抢占时变化

项目的 Engine/Scheduler 已经以多 sequence 的 iteration plan 为抽象；但当前生产 Paged K4 的算子能力仍限定为单 sequence、单 query token。两者必须分层表述：控制面支持 continuous batching，不等于某个候选 Attention kernel 已支持多 sequence。

3.5 Continuous batching 怎样完成一轮

  1. 读取所有 sequence 的 phase、剩余 Prefill、Decode 可运行状态、deadline 和 KV 占用，形成不可变 snapshot。
  2. 先依据显存块、最大 token 数和算子 capability 计算本轮预算，不能先选请求再祈祷显存足够。
  3. 在预算内组合 Decode 与 chunked Prefill；Decode 通常优先以控制 TPOT，Aging 则让等待过久的 Prefill 最终获得执行机会。
  4. 生成 iteration plan，并预留新 KV 块；此时正式映射尚未改变。
  5. 执行模型和必要的 Remap/Swap/Paged 动作；CUDA event 完成后才 commit 新映射。
  6. 移除完成/取消 sequence、回收引用归零的块，再进入下一轮。下一轮 batch 成员可以完全不同。

这解释了 AI Infra 中的核心矛盾：扩大 batch 往往提高 GPU 吞吐，却可能增加排队时间；过度偏向 Decode 会让长 Prefill 饥饿；过度塞入 Prefill 又会拉高活跃用户的 TPOT。因此调度目标不是单一“GPU 利用率最高”，而是在 SLO、容量、公平和吞吐之间求可行解。

3.6 Admission、Scheduling 与 Execution 的边界

Admission control（准入控制）决定新请求是否可以进入系统；Scheduling（调度）决定已进入系统的请求本轮谁运行；Execution（执行）把计划变成模型和 CUDA 工作。三者不能混为一个优先队列：准入错误会让承诺的 KV 超过物理容量，调度错误会造成饥饿或尾延迟，执行错误则可能留下半完成 GPU 状态。

自测：为什么“HTTP 同时来了 16 个请求”不能证明 kernel 的 batch 是 16？
答案请求可能仍在排队、Prefill、等待 KV 或已被背压；只有 iteration plan 中本轮实际进入模型的 active sequences/tokens 才构成执行 batch，还可能被后端继续拆成 micro-batch。

4. KV Cache：从内存问题到系统设计

M2 · KV Block Runtime：状态与容量平面
它接收什么？
sequence 的 token 位置、Prefix 命中结果、本轮容量 reservation，以及 Engine 提交或释放动作。
它产出什么？
逻辑块到物理块的 Block Table、refcount、可复用 Prefix、COW/Swap/Recompute 所需的资源计划。
它为什么存在？
KV 是生成过程必须保存的动态状态；按整段连续分配既产生外部碎片，也无法安全共享相同前缀。
原理是什么？
借鉴虚拟内存：逻辑地址与物理地址解耦；借鉴共享页：refcount 管生命周期；写共享页前 COW，容量不足时在搬运与重算间选择。
对应基础知识
操作系统分页/页表/缺页与 Swap；哈希表；引用计数；写时复制；摊还分析与资源守恒不变式。
代码与证据
server-kv-block-manager.*、Prefix Index、Swap Store；真实 Qwen 请求验证 21 个 Prefix block、324 token 共享且输出与 cold decode 一致。

4.1 逻辑块、物理块与 Block Table

逻辑块是某条序列看到的第 0、1、2…块；物理块是设备内存里真正占容量的块；Block Table是逻辑块号到物理块号的数组。类似操作系统页表，它允许逻辑上连续的 token 分布在不连续物理块中，减少必须寻找大段连续显存造成的外部碎片。

物理块记录引用计数 refcount。它表示有多少序列或索引仍指向该块；只有 refcount 归零才能回收。核心不变式是：每个有效映射都对应一个引用，空闲块不被任何有效映射引用。

4.2 Prefix sharing

多个请求常共享系统提示词或相同长前缀。Prefix Index 用 token 内容的稳定键查找已有块链；命中后增加 refcount 并复用 KV，而不是重新 Prefill。真实请求中验证过共享 21 个 Prefix block、324 个 token。Prefix 命中节省的是重复 Prefill 与重复 KV 容量，但查找、校验和生命周期维护也有成本，所以仍需门控。

4.3 Copy-on-Write（COW，写时复制）

若两个序列共享一个尚未填满的尾块，其中一个继续写入会污染另一个。COW 步骤是：分配新物理块 → 复制旧内容 → 等待复制在正确 stream 完成 → 将写者映射切到新块 → 旧块 refcount 减一。必须先完成复制再公开映射；否则其他线程可能看到未初始化数据。

白板不变式：共享块只能读；任何写入要求该映射独占，即 refcount==1。COW 后两个序列的逻辑内容相同，但物理所有权已分离。

4.4 Swap 与 Recompute

Swap把 KV 从 GPU 移到设备暂存、Host pinned memory 或持久存储，恢复时再搬回；pinned memory 是操作系统锁页的主机内存，GPU 可通过 DMA（Direct Memory Access，设备不经 CPU 逐字节参与的直接内存访问）搬运，适合异步拷贝。Recompute丢弃 KV，需要时重新 Prefill 原 token。选择取决于 KV bytes、带宽、固定 launch/I/O（Input/Output，输入输出）成本、预计复用距离和 Prefill 计算成本，并不存在永远更优的一项。

swap cost ≈ fixed + bytes / effective_bandwidth + queue/overlap cost recompute cost ≈ cached_tokens × prefill_ms_per_token

Swap handle 必须绑定模型身份、布局、校验和和生命周期。保存失败不能发布 handle，恢复失败要清理临时状态并回到可行的 Recompute，保证事务完整性。

4.5 显存到底由什么组成

推理显存不是只有模型权重。近似可以拆为：

VRAM ≈ model weights + KV cache + temporary activations + CUDA workspaces + graph buffers + allocator reserve

其中权重在模型加载后相对固定；KV 随活跃 sequence 的上下文增长，是服务端最重要的动态项；workspace 和 CUDA Graph buffer 又会制造不可忽略的峰值。只报告“KV 理论字节数”不能证明服务可容纳多少并发，因为真正的 OOM 由总峰值和分配器可用连续区间决定。

若模型有 L 层、每 token 有 Hkv 个 KV head、每个 head 维度为 D、每元素 b bytes，则单序列 KV 近似为：

KV_bytes = context_tokens × L × 2(K和V) × Hkv × D × b

多序列时应对各自实际上下文求和，而不是简单使用 最大上下文×最大并发；后者是连续预留常见的容量浪费来源。

4.6 内部碎片、外部碎片与可服务容量

内部碎片是已分配页内部未使用的空间，例如 page size=16 而序列最后一页只用了 1 token；外部碎片是总空闲显存足够，但被分割成许多小洞，找不到所需连续大块。分页主要缓解外部碎片，并把内部浪费限制在每条 sequence 的最后一页。

最后一页浪费 tokens = (page_size − context_tokens mod page_size) mod page_size 内部碎片上界 < active_sequences × page_size × 每token KV字节

因此评价 Paged 的系统价值不能只测单请求 kernel。还要构造不同长度 sequence 动态进入/离开的压力场景，报告峰值显存、已用页、最后页浪费、最大可服务并发、拒绝/OOM 次数。当前 Direct/Paged A/B 共用同一底层分配器，只能比较执行路径，不能从中推断容量或碎片优势。

4.7 多序列 KV 生命周期必须满足的守恒关系

  • 每个 sequence 的逻辑块链独立，不能因 batch 合并而共享可写尾页。
  • 物理页的 refcount等于所有 Block Table 与 Prefix Index 对它的有效引用总数。
  • 完成或取消只释放该 sequence 持有的引用；共享 Prefix 仍被其他序列使用时不能回收。
  • 抢占后的 Swap/Recompute 状态必须保留恢复所需身份，不能同时把 sequence 标为 runnable。
  • 页回收发生在 GPU 最后一次读取完成之后；CPU 删除映射不代表设备已经停止访问。

5. CUDA 基础与 Remap 算子

M3 · CUDA Remap / Swap：GPU 数据平面
它接收什么？
Block Manager 生成的 descriptor、真实 Attention K/V Tensor 地址、元素大小、stride、stream 和资源租约。
它产出什么？
完成 Remap/COW/D2H/H2D 的异步 GPU 工作，以及可供 Engine 等待和提交的 CUDA event。
它为什么存在？
块表只是元数据。物理 K/V 不随 C++ 映射自动变化，必须由正确处理布局、重叠和生命周期的真实后端完成搬运。
原理是什么？
aligned fast path 用 128-bit load/store 降低指令数；重叠映射使用 gather→staging→scatter 保证 snapshot 语义；stream 保序，event 建立跨 stream happens-before。
对应基础知识
计组存储层次、带宽与对齐；SIMT/warp；并发中的 happens-before；memcpy 与 memmove 语义；异步资源生命周期。
代码与证据
server-kv-block-cuda.cu 与 paged KV adapter；CPU oracle、memcheck/racecheck、CUDA-event 主结果和 NSYS 机制回放共同验证。

5.1 CUDA 执行词汇

kernel是在 GPU 上并行执行的函数。CPU 发起一次 kernel 得到一个 grid；grid 由多个 block/CTA 组成，CTA 是可共享 shared memory 并同步的一组线程；NVIDIA GPU 通常每 32 个线程组成一个 warp按同一指令执行。stream是一条按序的 GPU 命令队列；同一 stream 内天然有先后关系，不同 stream 需要 event 等依赖。kernel launch 通常异步，只说明提交成功，不说明 GPU 已完成。

内存层次：register 是线程私有最快存储；shared memory 是 CTA 内共享的片上存储；global memory 是容量大的显存。相邻线程访问相邻且对齐地址可形成合并访存，减少内存事务。CUDA event是插入 stream 的标记，可用于建立依赖或测设备时间。

5.2 Remap 在做什么

KV Remap 是按描述符把若干源物理块 Gather 到 staging，再 Scatter 到目标位置。Descriptor 保存源块、目标块、字节范围和布局，因此 kernel 不依赖硬编码映射。若源目标重叠，直接原地搬可能让前面的写覆盖后面尚未读取的数据；项目使用 snapshot/staging 语义，相当于并行版 memmove。

Block descriptors → Gather(source → staging) → event/dependency → Scatter(staging → destination) → commit mapping

5.3 为什么用 uint4

uint4 是 4 个 32-bit 无符号整数，总计 128 bit，也就是 16 bytes。地址、长度和 staging 都满足 16-byte 对齐时，一个线程可用一次 128-bit load/store 搬 8 个 FP16 元素，减少指令与地址计算。若不对齐，强制向量访问可能非法或分裂，因此自动回退逐元素标量路径；末尾不足 8 个 FP16 时也做边界保护。

这解释了数据：aligned small case 明显获益，而 misaligned case 每线程退化成 8-lane 标量循环，额外分支与组织开销使其不适合作为向量路径。正确做法是让 alignment 成为 capability gate，而不是宣称“向量化永远更快”。

5.4 正确性与性能分别怎么证

  • CPU oracle 对比所有元素；覆盖 identity、随机碎片映射、跨块、尾部、重叠和非法 descriptor。
  • Compute Sanitizer memcheck 检测越界/非法访问，racecheck 检测共享内存数据竞争；结果 0 error、0 hazard。
  • 无 profiler 的 CUDA event 给主性能估计；NSYS（Nsight Systems）用时间线核对 launch、memcpy、PID 和 stream 机制。
  • NSYS 可能改变时序，所以其 trace 不与主延迟表混合。

5.5 一个 GPU kernel 为什么会慢

不能看到耗时高就直接说“显存带宽瓶颈”。kernel 的时间可能受五类因素影响：

  1. Launch-bound：工作量很小，固定启动与调度成本占主导；常见于 batch 小、张量小。
  2. Memory-bound：搬运数据所需时间高于计算时间；需要 DRAM/L2 throughput 和 warp stall 等计数支持。
  3. Compute-bound：算术指令或 Tensor Core 已接近计算上限；提高带宽未必有效。
  4. Latency-bound：依赖链长或可运行 warp 太少，访存延迟无法被其他工作隐藏。
  5. Synchronization-bound：CTA 内 barrier、跨 kernel merge 或 host/device sync 使并行工作等待。

Occupancy（占用率）是一个 SM 上实际驻留 warp 数相对硬件上限的比例；它受寄存器、shared memory 和线程数限制。占用率低可能无法隐藏延迟，但占用率高不等于 kernel 一定快。算术强度是每搬运一个 byte 完成多少运算；Roofline 用它判断理论上更可能受计算上限还是带宽上限约束。

5.6 从症状到证据的性能诊断顺序

端到端回退 → 分解 queue / CPU plan / H2D-D2H / kernel / sync → NSYS 定位时间线与空洞 → NCU 查看目标 kernel 的吞吐、stall、occupancy → 检查 grid、shape、对齐和数据布局 → 提出一个可证伪修改 → 无 profiler 配对复测

NSYS 回答“时间花在哪个阶段、kernel 是否并发、是否发生同步”；NCU 回答“某个 kernel 内部为什么慢”。代码静态分析只能产生假设，例如“GQA 重复读 K/V”；只有硬件计数或隔离实验才能把它升级为机制结论。

6. Paged Decode Attention：模型侧算法与 CUDA 实现

ggml-cuda/fattn-paged.cuh、llama-context.cpp 与 server Paged adapter；24 个 CPU/CUDA oracle、跨页/反序物理页/分区边界测试和 H10→H13 服务 A/B 决定它保持 evidence-gated。

6.1 它与 Remap 的根本差别

Remap 先把非连续 KV 搬到目标布局，再由普通 Attention 读取；Paged Decode Attention 让 Attention kernel 自己查询 page table，直接读取物理页。前者付出搬运成本但后续计算访问规则简单；后者省掉中间搬运，却在每个历史 token 上增加页表寻址，性能取决于上下文、布局和 KV 复用。

6.2 K1 kernel 的线程映射

K1 表示第一版直接 kernel：一个 CTA 负责一个 (sequence, query_head)，CTA 内线程数等于 head dimension，每线程负责一个维度。grid block 数为 batch_size × query_heads。Query head 先按 GQA 比映射到 KV head，然后逐 token 通过：

logical_page = token / page_size offset = token % page_size physical = page_table[sequence, logical_page] kv_index = (((physical × page_size + offset) × Hkv + kv_head) × D + dim)

页大小固定 16；支持 D=64/128。真实 0.5B 生产路径用 D64。page table、context length、shape、dtype 与完整 GPU offload 都先验证，超出支持域在 KV mutation 前 fail closed。

6.3 online softmax 为什么数值稳定

普通 softmax 需要先得到所有 score，再减去最大值。Paged kernel 希望单遍流式读取 token，不保存完整 score 数组，于是维护运行最大值 m、归一化分母 l 和未归一化加权和 o。新分数 s 到来：

m' = max(m, s) α = exp(m - m') （旧权重缩放） β = exp(s - m') （新权重） l' = αl + β o' = αo + βv final output = o / l

减去当前最大值使指数不超过 1，避免 exp(很大正数) 溢出。项目用 FP32 保存 score、运行状态和输出累积，即使输入 K/V 为 FP16，也降低累计误差。CPU FP32 oracle 的最大绝对误差为 3.6×10⁻⁸。

6.4 从 benchmark 到生产 adapter

第一阶段用 9 个 regime、360 条 observation 验证数学正确性和不同上下文形状。第二阶段把 K1 接进真实 Qwen2.5-0.5B production graph：10 组 17-token 跨页 Direct/Paged AB/BA，输出逐字一致，Paged graph entry 10 次、fallback 0；独立 NSYS replay 记录 24 个 layer launch，与 24 层模型一致。

生产结果触发了关键工程机制：Paged P95 为 29.210 ms，Direct 为 27.354 ms，超过预注册 +5% promotion limit，因此策略保持默认 Direct、Paged 保留 opt-in。面试中的正面表达是：我不仅实现了算子和生产接入，还实现了数据驱动的 promotion gate，证明“能运行”与“应默认上线”是两个验收阶段。

6.5 K2：从正确 K1 到可替换的生产算子

K2-T2 中的 T2 表示一个 CUDA thread block（CTA）包含两个 warp，每个 warp 负责一个 query head。Qwen2.5-0.5B 有 14 个 query heads、2 个 KV heads，即每 7 个 query heads 共用一个 KV head。K1 为每个 query head 单独装载 K/V，所以每 KV head 要装载 7 次；K2 每个 CTA 让两个 query heads 复用一次 shared-memory staging，因而分成 4 个 tile、装载 4 次。K 采用按维度转置的 shared-memory 布局，softmax 的 max 与 sum 使用 warp shuffle 归约；这减少的是代码层可确认的重复装载和同步，不能在缺少 NCU counter 时写成“已测得 DRAM bytes 或 bank conflict 降低”。

正式 v2.10 在同一长驻服务进程内按固定随机种子运行 30 组 K1/K2 配对。每 arm 清空 slot，完成 1 次完整 prompt、4 次 cached warm request，再记录 16 次 context17 cached one-token 请求。每 variant 的 480 个测量响应逐字一致，并累计 600 次请求级 Paged graph entry、0 fallback；请求级 median 为 6.900/6.938 ms（K2 回退 0.55%，配对簇 bootstrap 回退 95% 上界 2.86%），P95 为 30.102/30.559 ms（回退 1.52%）；PID 隔离 NSYS 中相同 480 次目标 kernel 总时长从 8.174 ms 降至 4.051 ms（-50.44%）。它通过的是“median 回退 95% 上界与 P95 点估计回退均不超过 5%，且 kernel 至少降低 20%”的 K2-over-K1 替换门槛，不代表 Paged-over-Direct 已通过，也不代表端到端普适加速。

如果面试官追问实验迭代：v2.5 的 kernel 虽下降 47.0%，客户端 median 仍回退 20.8%，因为单次微秒级算子差异会被 HTTP/调度噪声淹没；v2.7 又因 host gate 只允许 context17 进入 K2 而被判无效。扩展并重新做 CPU oracle 后，CUDA graph node trace 证明每个 cached 请求只有一次 Paged 动作，不能把一个八 token 请求说成八次 K2 干预。最终保持门槛不变，在同一 context17 用户场景中每 arm 重复 16 次真实请求，以 480 条原始请求/variant 估计请求级分布，并用 pair-cluster bootstrap 保留配对结构。v2.4 的预注册时间晚于结果，只算无效而非预注册失败；全部失败、无效和中止实验均留档，避免结果导向删数。

6.6 K3/K4：长上下文为什么必须改变执行结构

旧 K2 在 512–2048 token 的 H10 中相对 Direct 中位回退 +50.35%。根因不是 Prompt 文本本身，而是执行结构：每个 CTA 只覆盖两个 Query Head，真实 GQA7 中同一 KV Head 的 K/V 仍被分四次加载；QK/PV 计算较标量化；固定 partition 又产生多余 CTA、scratch 写回和 merge 成本。

K3先用 half2 把两个 FP16 元素作为一个向量访问，减少标量访存和指令。K4进一步按真实模型几何重排：一个 256-thread CTA 包含 8 个 warp，其中 7 个 warp 分别负责同一 GQA 组的 7 个 Query Head，第 8 个 warp 协助 K/V 搬运；整组只加载一次 K/V。设备读取真实 context 后，短一些的序列使用 64-token partition，长一些的使用 128-token partition；host 不同步，CUDA Graph 不因每次长度变化而重建。

旧 K2：1 CTA = 2 query heads；每 KV head 约加载 4 次 K4： 1 CTA = 完整 7-query-head GQA group；每 KV head 加载 1 次 grid： sequence × KV-head group × effective partition

24 个 production CPU/CUDA oracle case 覆盖 1、页边界、tile 边界、partition 边界直到 2048 token，多页时反转物理页序，全部通过。H13 使用 18 个来源绑定真实文档 Prompt、12 个严格平衡进程块、432 个 workload-arm 单元和 3456 个测量请求，把主中位回退降至 +3.98%，95% CI 为 [+2.50%, +5.38%]。这证明重构显著缩小差距；但 CI 上界仍高于 +5% 门，所以不能说 Paged 已严格占优。

6.7 怎样从 batch=1 正确性原型演进为多序列生产路径

用单 sequence 首先验证页表、GQA、causal mask 和 online softmax 是合理的；旧设计的问题是算子接口只有一个 page_table 和一个 context_length，于是 batch=1 从测试条件变成了架构限制。现在的生产布局把它改为二维行主序 block_table[sequence][logical_block] 和 context_lengths[sequence]，batch=1 只是下式在 N=1 时的退化情况：

grid = sequence × KV-head-group × partition per-sequence metadata: block_table[N][max_blocks] context_lengths[N] Q/output stride[N] partial_state[N][head][partition]

为什么这些维度必须同时改？只扩展 page table 而不扩展 Q/output stride，会让不同序列读到同一个 Query 或写坏彼此输出；只扩展主 kernel 而不扩展 scratch，merge 会混合两条请求的 online-softmax state；仍用第 0 条序列的 context 裁剪所有 table row，又会让较长序列静默少算。CPU reference 因此也必须按 query index 取自己的 table row 和长度，不能让 oracle 与 CUDA 共享同一个错误假设。

服务端采用图级 all-or-nothing gate：ubatch 中每个 token 必须属于不同 sequence，且每条 sequence 都已有 Paged 决策；prefill、同一 sequence 多 token 或混合动作整图回退。这样避免一张 attention graph 内同时解释为两种 KV 布局。完成或取消的 sequence 下一轮可以离开 batch，但它的页只有在最后一个 GPU reader 完成后才能回收；graph reuse key 仍要包含 Paged topology。

已完成与尚未证明：K1–K4 均通过 batch 1/2/4/8 的 production CPU/CUDA oracle，而且同时覆盖 unified [D,B,H,1] 与服务默认 non-unified [D,1,H,B]。真实 llama-server -np 8 用 8 个不同 resident prefix 形成一个 batch=8 graph；不能只看 graph admission counter，所以另从 CUDA backend 记录到 24 个逐层 Paged dispatch 和 192 个 sequence-layer dispatch。Direct/Paged 输出与 cache length 逐项一致，top-64 至少重叠 55、最大 logprob 误差 0.6900（门限 48/1.0），零 fallback。这证明功能与已声明数值边界，不证明 batch 性能已经优于 Direct；既有 H7/H13 性能结果仍是 batch 1。

6.8 大 batch 下 Paged 为什么可能更有利，也可能仍不赢

batch 增大会产生三种潜在收益：更多 CTA 填满 SM，使访存延迟更容易被其他 warp 隐藏；页表与 launch 固定开销被更多 sequence 摊薄；不同长度 sequence 的分页分配开始体现容量与碎片价值。但 Direct 同样会因 batch 增大提高 GPU 利用率，因此“batch 大”不是 Paged 必胜条件。

应采用二维以上矩阵，而不是只测一个 batch：

维度建议取值为什么
active sequences1/2/4/8/16观察占用率、吞吐与排队拐点
context128/512/1024/2048，且混合长度区分页寻址固定成本与长序列工作量
布局连续页/随机非连续页/碎片压力区分 arithmetic 差异与分页管理价值

报告必须同时给出吞吐、TTFT、TPOT、P50/P95、峰值显存、内部/外部碎片、最大并发和 OOM/拒绝率。若只报告 kernel time，就没有覆盖 Paged Attention 的系统价值。

6.9 怎样与 upstream 做严格公平对比

Upstream baseline是未经本项目修改、固定 revision 构建出的 llama.cpp 可执行文件。它与“当前 fork 中选择 Direct action”不是同一概念：后者适合隔离 Paged kernel 差异，前者才能回答整个 fork 是否优于原仓库。

  1. 固定 upstream revision、编译器、CUDA、编译选项、模型哈希、GPU 功耗状态与服务参数。
  2. 分别构建纯 upstream 与当前 fork，记录二进制 SHA-256；不能让两臂加载不同模型或 tokenizer。
  3. 使用同一冻结 workload、相同请求顺序和相同 warm-up；独立进程时平衡先后顺序。
  4. 分别比较功能等价输出、请求指标和资源指标；不能把 fork 多出的缓存命中与 upstream 冷请求混在一起。
  5. 报告点估计、置信区间、P95 和最差 workload；严格占优要求预先定义所有必须通过的门，而不是跑完后挑指标。

当前 H13 是同一 fork 内 Direct/Paged 的受控比较，尚不是纯 upstream executable 对照；这不影响它定位 K4 算子差距，但限制了“整个项目超过 upstream”的结论。

7.2 为什么先 gate 再打分

Capability gate是合法性/资源门：一个动作若当前不可执行，就必须在评分前屏蔽，而不是让它因预测成本低“获胜”后再临时补救。例如 Paged shape 不支持、Remap staging 空间不足、Swap handle 校验失败，都应得到结构化拒绝原因。这样模型误差不会突破正确性边界。

7.3 九维特征与按动作 Ridge

请求快照包含 cached tokens、expected decode tokens、KV bytes、page count、contiguous pages、reuse distance、reuse probability、KV pressure 等运行特征，并结合带宽、launch 和单位 token 计算成本形成固定九维模型输入。每个动作有独立模型，因为“bytes 对 Remap 的影响”和“tokens 对 Recompute 的影响”并非同一组系数。

线性回归用 ŷ=wᵀx 预测成本。Ridge regression 在平方误差后加 λ||w||²：

w = (XᵀX + λI)⁻¹Xᵀy

λ 是正则强度；它使少样本或特征相关时矩阵可逆，并抑制极端系数。在线更新不是每次保存全部历史，而是累计 A=XᵀX+λI 与 b=Xᵀy，得到 w=A⁻¹b。

7.4 置信半径、冷启动与 fail closed

点预测不表达不确定性。项目计算与 sqrt(xᵀA⁻¹x) 相关的置信半径：新特征与历史覆盖差异越大，半径越大。最小化成本时，切换条件不是“候选预测略低”，而是候选的保守优势超过 uncertainty 与 switch margin。样本不足属于 cold start；非有限输入、OOD（Out-of-Distribution，超出训练分布）、低置信或执行失败都回到当前阶段的安全 H0 动作。

7.5 H0/A1/T1/L1 是什么

  • H0：固定、安全的生产基线策略。
  • A1：只使用分析公式，例如 bytes/bandwidth 的策略。
  • T1：按训练数据把特征空间分桶、为每个桶保存动作成本中位数的离线查表模型；评估时冻结表，不再看测试标签。
  • L1：按时间顺序在线更新，并受置信下界约束的 per-action Ridge。

四者必须在同一 cost boundary、特征和 trace 切分下比较。Issue #6 正式 replay 有 40 条隔离 trace（20 train、20 evaluation）和 200 组原始观测；当时的真实动作覆盖 Direct、device Swap、host Swap、Recompute，Remap/Paged 由 capability mask 排除。Issue #7 再单独加入真实 Remap 与 Paged production adapter，不能把两个实验的动作覆盖事后混写。统一 chooser 的 5 个 regime 共执行 500 万次，最差 P99 1.000 微秒、零热路径堆分配；决策时间占 scheduler/action 的 P99 为 0.0644%。

7.6 backend-local Benefit Gating

另一个更靠近真实 Prefill 决策的控制器比较 upstream greedy plan 与 CacheFlow shadow plan。shadow plan只计算替代方案、不立即产生副作用，因此可在不改变生产行为时积累反馈。CPU 和 CUDA 分别维护模型，因为两者成本分布不同。

有限探索是在安全预算内主动收集少量缺失动作样本；不是随机把所有流量暴露给未知方案。distribution shift是在线特征/残差分布变化；连续异常触发 cooldown 和安全回退。长期实验 53 waves 中，稳定阶段产生 26 次探索、125 次 positive-lower-bound 决策、最长连续正下界 35；shift 阶段 CacheFlow/positive 为 0，并触发 3 次 safety fallback，展示了“学会启用，也学会停止”。

8.3 Williams design 解决什么混杂

短周期门控有 8 个 backend×mode 联合 treatment。若固定顺序执行，位置效应和前一个 treatment 的余热会混入结果。Williams design 是一种平衡交叉设计：每个 treatment 在每个进程位置出现相同次数，每条“前一个→当前”有向边也均衡。本实验 16 trial 构成两个完整 block；64 个 treatment×position 单元和 56 条有向前驱各覆盖 2 次，trial 间 washout 1 秒。这样可以将“策略差异”与“顺序/前驱效应”更好地区分。

8.4 Oracle regret 与 harmful decision

对同一快照，可行动作集合为 F，实际选择 a，成本为 C：

regret = C(a) - min C(feasible action) ≥ 0

oracle是事后知道所有可行动作实测成本的最优选择，只用于离线评估；线上不能看到未执行动作的真实成本。Regret 比“动作分类准确率”更合理，因为选错相差 0.01 ms 与选错导致几十 ms 损失不应同权。Harmful decision 是相对安全 H0 超过预注册百分比或 SLO 预算的选择。

8.5 服务级 CUDA 因果链怎么读

因果链按“干预→中介→结果”组织：强制 CacheFlow 改变 decision；中介包括 prefill chunks/tokens、KV launches/copy bytes/CUDA event；结果是 Engine execute 与请求 TTFT。3 个 no-profiler pair 给主效应，相同 seed/config 的 profiler replay 用 6 个 server PID（Process ID，操作系统进程编号）、72 个 request ID 关联 scheduler、KV action 和 NSYS timeline。

该正式 run 中：decision +20、chunks +30、tokens -86、runtime KV launch +0、copy bytes +10,518,500、CUDA event -1.040 ms；TTFT P95 +126.932 ms，Engine execute +146,493 μs；profiler replay 有 42 次 PID-filtered 自研 launch。它说明局部 CUDA 时间下降并不足以抵消调度形状与额外数据动作，正是本项目转向统一成本决策而非单点 kernel 崇拜的依据。

9. 如何证明这些不是“跑了个 demo”

9.1 四层证据

  1. 数学正确性：CPU FP32 oracle、确定性输出、边界/随机/poison case。
  2. 内存与并发正确性：refcount/COW 不变式、故障原子回滚、memcheck/racecheck。
  3. 机制证据：NSYS 中真实 PID、request ID、kernel 名、launch 数和 stream 时间线。
  4. 用户结果：无 profiler 请求 TTFT/P95、吞吐、regret、真实应用 journey。

四层不能互相替代：输出一致不证明快；kernel 快不证明请求快；Prometheus counter 变化不证明特定 kernel；profiler trace 也不应当作无扰动主延迟。

9.2 Artifact（实验制品）为什么可信

正式 artifact 保存 protocol/config、manifest、raw CSV/JSONL、derived summary、report、环境、代码 revision 和 SHA-256。SHA-256 是内容哈希：文件任一字节改变几乎都会得到不同摘要。验证器不只检查“文件存在”，还从 raw row 重算 summary、检查 trial/request/PID 基数、重解析 NSYS SQLite，并用 tamper test 验证即使攻击者同步更新文件哈希，语义不一致仍会被拒绝。

9.3 个人贡献如何与上游区分

不要用“整个 llama.cpp 都是我写的”。正确表达是：上游提供 GGUF/GGML、基础模型执行和 server 语境；个人拥有的深模块是 inference scheduler/iteration/engine、KV block/prefix/swap、benefit policy、统一 action policy、Paged layout/CUDA kernel、实验 harness/validator 和真实应用集成。面试时沿具体文件、接口和一次调用链解释，代码所有权比总行数更可信。

10. 高频追问与完整回答

Q1：llama.cpp 本来做什么，你的项目和普通 Agent 有何不同？

llama.cpp 是在本地 CPU/GPU 上加载 GGUF 权重并执行 Transformer 推理的 C/C++ 引擎，也包含采样与 HTTP server。GGUF 是保存模型张量与元数据的文件格式；GGML 是 llama.cpp 体系中的张量计算与后端框架。Agent 是调用模型、工具和记忆完成任务的上层应用；本项目位于模型服务和运行时层，处理 batch、KV、显存、CUDA kernel 与在线动作选择。学习助手只是验证流量入口，不是项目核心。

Q2：为什么不能只复现 vLLM/PagedAttention？

复现能证明理解接口，但个人贡献有限。我选择在 llama.cpp 的真实约束下重构调度和 KV 生命周期，再实现自有 Remap/Paged kernel、策略与证据合同。研究问题不是“能否复制”，而是不同 KV 动作在本机模型和负载下何时值得执行。

Q3：为什么分页能减少碎片？

请求不再要求一段与整个上下文一样长的连续物理区间，只需若干固定大小空闲页。它主要缓解外部碎片；最后一页未填满仍有内部碎片，页表查询也有成本。

Q4：COW 的并发 bug 最可能在哪？

新块复制完成前就发布映射，或 refcount 更新与映射提交不是同一事务。解决方式是 shadow plan、同 stream/event 依赖和 commit 后再释放旧引用。

Q5：为什么 Remap 需要 staging？

源和目标块可能重叠。若直接并行写，某线程可能覆盖另一线程稍后要读的源数据。先 Gather 到独立 snapshot，再 Scatter，相当于保证 memmove 语义。

Q6：128-bit 就一定快吗？

不一定。需要 16-byte alignment、足够连续元素和合适规模。小 aligned case 减少指令明显；错位时退回 8-lane 标量循环，组织开销反而更高。因此 alignment 是 gate，数据也保留该反例。

Q7：Paged kernel 为什么最初一个 CTA 对应一个 Query head，后来又改掉？

K1 让 D 个线程直接并行一个 head 的点积和 V 累积，结构简单，适合作为正确性基线；但 GQA7 下七个 Query Head 共用一个 KV Head，K1 会重复读七次 K/V。K2 只把重复次数降到约四次；K4 才用一个 256-thread CTA 覆盖完整 GQA 组，让七个计算 warp 共享一次 K/V 加载。最小正确性映射适合验证，不等于最终性能结构。

Q8：online softmax 与普通 softmax 等价吗？

代数上等价。每次最大值变大时，用 α=exp(old_max-new_max) 同步缩放旧分母与旧加权和，再加入新项 β。最终 o/l 就是对全部 score 做稳定 softmax 后的加权 V。

Q9：为什么 Paged 已接生产却不默认选？

生产接入和 24 个 oracle case 证明路径与正确性；默认 promotion 还要求性能和尾部风险门。K4/H13 已把旧 K2 的长上下文中位回退从 50.35% 降至 3.98%，但 95% CI 上界 5.38% 仍超过预注册 +5%，P95 回退也有 13.34%，所以保持 opt-in。功能完成、算法改善和生产晋级是三个不同结论。

Q10：下一步如何优化 Paged？

sequence-aware 接口和 batch 1/2/4/8 正确性已经完成，下一步不再重复这一项，也不再优先调 tile 常数，因为 H14 已否证 64-token tile。算子侧应复用 upstream vector attention 的成熟 QK/PV 主体，只把连续 K/V 地址生成抽象为 page-indirect accessor；实验侧扩展到 batch 16、mixed length、动态加入/取消，并同时量峰值显存、碎片、吞吐、TTFT/TPOT 和拒绝率。只有这样才能评价 Paged 的容量收益及其是否足以覆盖页表寻址成本。

Q11：Ridge 为什么比神经网络合适？

特征只有九维、反馈少且在线决策要求微秒级、零分配和可解释回退。Ridge 的计算和状态固定，能增量更新并给出与 A⁻¹ 相关的不确定性。神经网络在当前数据规模会增加训练、校准和部署复杂度，收益没有证据。

Q12：为什么按动作分别建模？

不同动作的成本生成机制不同：Remap 更依赖 bytes/fragmentation，Recompute 更依赖 cached tokens/prefill cost，Swap 更依赖带宽和固定 I/O。一个共享线性模型容易把不同斜率混在一起。

Q13：置信下界如何防止误切换？

对成本最小化，可比较基线的保守低成本与候选的保守高成本，或等价比较收益的 lower bound。只有考虑 prediction radius 和 margin 后仍明确更优才启用；否则 uncertainty fallback。它不是形式化零风险证明，而是工程保守门控。

Q14：如何处理 concept drift？

监控预测残差及其连续异常 streak；达到阈值进入 cooldown，停止 learned exploitation，回到 H0，同时保留按 backend/model/schema 隔离的状态。长期 53-wave 实验中 shift 阶段没有正下界启用，并触发 3 次 safety fallback。

Q15：为什么不是随机切 80/20 数据？

同一 session、prefix family 和相邻时间行高度相关，随机拆行会泄漏。正式评估按完整 trace 分组，训练在过去、评估在未来；同一 trace 的所有动作 observation 位于同一 split。

Q16：paired bootstrap 为什么重采样 pair 而不是单行？

实验单位是共享条件的 baseline/treatment 对。拆开重采样会破坏配对相关性，重新引入环境噪声。应先算每对差值或改善率，再对完整 pair 重采样。

Q17：NSYS 与 NCU 区别？

Nsight Systems（NSYS）看系统时间线：CPU thread、CUDA API、kernel、memcpy 和并发关系；Nsight Compute（NCU）深入单 kernel 的硬件计数器，如 occupancy、DRAM/L2 throughput、warp stall。项目用 NSYS 完成 launch/因果关联；若被追问 memory-bound，需要 NCU 的硬件计数才能下结论，不能拿逻辑 payload/time 代替。

Q18：为什么 profiler 数据不作主性能结果？

profiler 会注入 hook、序列化或采样开销，改变绝对时延。无 profiler paired run 估计效果，profiler replay 只验证机制，二者用相同 seed/config 但分开报告。

Q19：服务因果链告诉了你什么？

强制策略确实改变 decision、prefill shape 和 KV 数据动作，但局部 CUDA-event 改善与请求 TTFT 不同层。它促使统一模型使用完整 action boundary，而不是只用 kernel time 打分。

Q20：500 万次是不是 500 万次真实请求？

不是，是五个 regime 的纯 chooser 热路径调用，用来测 P99 与 allocation；真实动作比较另有 40 trace、200 observation。主动区分这两个样本口径能避免夸大。

Q21：如何保证决策不拖慢 scheduler？

固定六动作和九维数组、无 heap allocation、无文件 I/O、决策模块不执行 CUDA synchronize。实测最差 P99 1 微秒，占对应 scheduler/action 时间 P99 0.0644%，低于预注册 50 微秒和 1% 预算。

Q22：最有创新性的点是什么？

不是某一个孤立 kernel，而是把模型侧直接分页 Attention、系统侧 KV 生命周期、CUDA 数据移动和在线成本学习放进同一个可行性优先的动作空间，并以真实服务因果链和可重算 artifact 决定 promotion。它连接了模型算法、AI Infra 与科研方法。

Q23：你遇到最难的工程问题是什么？

异步 CUDA 与事务状态的一致性：launch 成功不等于完成，取消/失败可能发生在映射更新中间。我把资源变化变为 shadow plan，并用 stream/event 建立 happens-before，只在设备动作完成后 commit；失败路径不公开半成品状态。

Q24：如果换 H100 或更大模型会怎样？

架构和协议可复用，但数值必须重新标定。更大模型改变 Hq/Hkv/D、KV 容量、计算/带宽比和 occupancy；H100 还改变带宽与调度特性。因此保留 capability gate、model/backend 隔离和重新预注册实验，而不是外推 RTX 4050 数字。

11. 深挖附录：系统、CUDA、机器学习与统计

11.1 调度器如何做一次可行计划

调度器输入不是 HTTP 文本，而是一组请求状态：Prefill 还剩多少 token、Decode 是否 runnable、deadline、已等待轮数、KV 已占块、预计新增块和是否可恢复。输出是本轮 iteration plan，即哪些 sequence 进入 batch、各处理多少 token、需要哪些 KV 动作。简化伪代码如下：

snapshot = read_runtime_state()
budget = capacity(snapshot.free_blocks, max_batch_tokens)

for seq in rank_by(deadline, aging, phase):
    demand = estimate_next_iteration(seq)
    if demand fits budget:
        plan.admit(seq, demand)
        budget -= demand
    else if seq can preempt safely:
        plan.preempt(seq, choose_swap_or_recompute(seq))

validate(plan)       // 不改变正式状态
execute(plan)        // GPU / store 动作
commit(plan)         // 成功后一次性发布

estimate_next_iteration 必须在执行前估算新增 token 对应的块数。若 block size 为 P，序列已有 T token，本轮追加 Δ，新增块近似：

new_blocks = ceil((T + Δ)/P) - ceil(T/P) 若尾块共享且本轮会写，还要额外预算 1 个 COW block。

复杂度取决于请求排序与候选扫描：若对 N 个请求排序，常见为 O(N log N)；计划内 Block Table 更新与触及块数线性相关。真正重要的是热路径不能随总历史 token 逐元素扫描，应该用已聚合元数据。

11.3 Prefix Index 的键、碰撞与失效

Prefix 复用不能只用“长度相同”判断。键至少要绑定 token 序列内容、模型/adapter 身份、KV layout 与可能影响表示的配置。哈希碰撞意味着不同输入得到同一短摘要；工程上需存长度与内容验证或更强复核，不能把哈希相等直接当语义相等。模型卸载、layout version 改变或块内容失效时，Index entry 必须同步失效；否则会复用语义不兼容的 KV。

11.4 Swap/COW 的异常路径推演

  1. 分配新块失败：旧映射未变，直接返回容量不足或选择其他 preemption 动作。
  2. 异步复制 launch 失败：释放 reserved block，不减旧 refcount。
  3. launch 后设备执行失败：通过 event/status 在 commit 前发现，丢弃新块。
  4. commit 时请求已取消：不再发布给请求；回收计划资源，取消状态保持终态。
  5. Swap checksum 不一致：拒绝恢复，不让损坏 KV 进入模型；在 phase 合法时转 Recompute。

11.5 CUDA 内存访问如何影响 Remap

GPU 一次 global memory 访问会按硬件事务粒度服务整个 warp。若 32 个线程访问连续、对齐地址，事务可以合并；若地址随机分散，可能需要更多事务。Remap 的物理块碎片不必然导致一个 warp 内也碎片：descriptor 可以让一个 CTA/warp 在单个块内部连续搬运，再切换块。因此设计重点是让内层 lane 连续、外层 descriptor 处理块级不连续。

有效 payload bandwidth可写为 逻辑搬运字节/CUDA-event 时间，用于同一 kernel 版本比较；它不等于 DRAM 物理带宽，因为缓存命中、读写放大和计时边界未知。若要声称 memory-bound，需要 NCU 的 DRAM throughput、L2 hit、memory pipe utilization、warp stall 等硬件计数，再结合 roofline。Roofline是把算术强度（每搬一个 byte 做多少运算）与硬件计算/带宽上限比较的模型。

11.6 CUDA 同步：四个常见错误

  1. 把 cudaGetLastError() 当成 kernel 已完成；它主要报告 launch 配置错误，异步执行错误常在后续同步暴露。
  2. 在 scheduler 热路径调用全设备 cudaDeviceSynchronize()；这会阻塞所有 stream，破坏并发。
  3. 跨 stream 使用同一 staging buffer 却没有 event 依赖；会产生 read-after-write/write-after-read hazard。
  4. 计时只包住 CPU launch；得到的是 enqueue time，不是 device execution time。

推荐关系是 producer stream record event，consumer stream wait event。这样只同步真正相关的依赖，不阻塞整个设备。

11.7 Paged K1 的逐步执行例子

设 page size=16，某序列 context=17，页表为 [5,2]。token 0–15 在 physical page 5，token 16 在 page 2。当前 Query head 8，在 Hq=14、Hkv=2 时 group size=7，因此它使用 KV head floor(8/7)=1。kernel 对 token 16 计算：

logical_page=16/16=1；offset=0；physical=page_table[1]=2 kv_index=(((2×16+0)×2+1)×64+dim)

“17-token 跨页”之所以是关键测试，是因为 16-token 恰好只访问一页，不能证明第二个页表项真的进入数据路径。生产 v1.0 因未跨页被降为审计记录，v1.1 固定 17 token 才形成有效跨页证据。

11.8 online softmax 手算

假设两个 score 为 2 和 3，Value 标量为 10 和 20。第一项后 m=2,l=1,o=10。第二项到来：m'=3，α=e^(2-3)=e^-1，β=1，所以 l'=e^-1+1，o'=10e^-1+20，输出 o'/l'。这与普通 softmax 的 (10e²+20e³)/(e²+e³) 同时除以 e³ 完全相同。

11.9 K1、K2、K3、K4 的研究路线

  • K1 one-CTA/query-head：简单、正确性易验证，是可解释 baseline。
  • K2 two-query-head tile：两个 warp 协同加载 K/V，把 GQA7 的每 KV Head 重复装载从 7 次降到约 4 次；在 context17 内部替换 K1。
  • K3 half2 vectorization：以两个 FP16 为一组访问并保留 partition/merge，为整组 GQA 映射准备向量路径。
  • K4 full-GQA CTA：一个 256-thread CTA 覆盖 7 个 Query Head，整组加载一次 K/V，并按 context 设备侧选择 partition；H13 把旧 K2 回退从 50.35% 降至 3.98%。

选择顺序由数据决定：短 context 的 K2 kernel 时间下降 50.44%，但 H10 暴露其长上下文执行结构仍不合理，于是 K4 按真实 GQA7 几何重构，而不是继续扩大二-head tile。H14 又验证 64-token tile 没有改善并被回退。这条路线展示“先由结构和数据提出假设，再保留失败实验”，不是把 K1、K2、K3、K4 当作数字越大越先进。

11.10 Ridge 的一个两特征例子

为便于手算，假设只用 x=[1, KV_MB]，观察 Remap 1 MB 用 0.1 ms、2 MB 用 0.15 ms。普通线性拟合试图得到固定成本与每 MB 成本；Ridge 在样本少时把两个系数向 0 收缩，避免仅凭两个点学出极端斜率。真实项目九维特征先归一化，否则 kv_bytes 以百万计、reuse_probability 在 0–1，会导致数值尺度失衡和正则作用不均。

在线 observe 只能使用真正执行动作的 observed cost。未执行动作的成本不可伪造为标签；完整 oracle regret 来自隔离 paired replay，而不是普通线上 chosen-only feedback。

11.11 探索—利用与保守门控

利用（exploitation）选择当前估计最好动作；探索（exploration）选择信息不足动作以减少未来不确定性。纯利用可能永远不给新动作机会，纯探索会伤害用户。本项目以次数、频率、风险预算和 capability gate 限制探索；真正 learned exploitation 要求 positive lower bound，而不是把 exploration 计成“模型确信获益”。

短周期实验中 CPU 有 43 次有限探索，CUDA 为 0 次 probe 并 fail closed；这说明不同 backend 的风险状态相互隔离。CUDA 8 个 harmful trials 中 wrong enable 为 0，即有害条件没有被非探索 learned decision 错误开启。

11.13 Median、P95、CI 与 effect size

Median（中位数）一半样本在其上、一半在其下，对极端值稳健；P95关注尾部，但小样本 P95 很不稳定；effect size是差异大小，如改善百分比或毫秒差；confidence interval表示估计的不确定范围。统计显著不等于工程重要，因此项目另设 materiality gate，例如至少 10% 才把 Remap regime 称为 material win，Paged production 则用 +5% regression limit。

11.14 如何读“局部变快、整体变慢”

设总延迟 T=T_queue+T_plan+T_copy+T_model+T_sync。Remap kernel 的 T_copy 降低，但策略可能产生更多 chunk、更多 bytes 或改变 batch，使 T_queue/T_model 增加；总和仍可能上升。这不是矛盾，而是优化层级不同。Amdahl 定律也说明：若某局部只占总时间比例 p，该部分加速 s 倍，总加速最多为：

Speedup_total = 1 / ((1-p) + p/s)

例如局部占 10%，即使无限加速，总体最多约 1.11 倍。因此简历写“KV Remap microbenchmark +57.10%”比写“推理加速 57.10%”更专业。

11.15 Prometheus Counter、Gauge 与 Histogram

Counter只单调增加，适合 decision、fallback、bytes total；进程重启可归零。Gauge可增可减，适合当前 confidence 或 queue size，但只看最后值不能证明过程发生多少次。Histogram用累积 bucket 记录观测分布，并带 count/sum；P99 可从 bucket 重算。项目保存 chooser 的完整 bucket/count/sum，并验证 bucket 总计与 decision counter 一致，避免只抄一个漂亮 P99。

11.16 面试中如何解释研究性

科研性来自可证伪问题，而不是“用了论文名词”。本项目的链条是：提出 H1 向量化在 aligned regime 有材料性收益；H2 用 profiler 区分 launch 数与单 launch 机制；H3 检验直接分页 Attention 是否省去 Remap 后更快；H4 将多动作纳入统一 cost boundary；H7 把 Paged 接入生产并用 promotion gate 验证。每一步都有 protocol、对照、阈值、raw evidence 和下一假设。

11.17 简历逐条“证据四元组”

回答任何 bullet 都按四元组：代码对象—核心不变式—实验规模—关键数字。例如：

  • Remap：llama-kv-cache*/CUDA descriptor → overlap 保持 snapshot 语义 → 160 no-profiler rows + 4 traces → aligned-1 +57.10%。

11.18 更多基础压力题

Q25：FP16 与 FP32 有什么区别？

FP16 用 16 bit 表示浮点，容量和带宽约为 FP32 一半，但指数/尾数精度更低。KV 以 FP16 存储节省显存；softmax 的最大值、分母和累积用 FP32，降低长序列求和误差。

Q26：为什么除以 √d？

若 Q/K 各维近似独立、方差为 1，点积方差随 d 增长；除以 √d 把尺度拉回稳定范围，避免 softmax 过度饱和、梯度/概率极端。

Q27：内部碎片与外部碎片？

内部碎片是已分配页最后未用空间；外部碎片是总空闲足够但缺少大连续区间。固定页主要缓解外部碎片，不能消除最后一页浪费。

Q28：refcount 能否单独解决线程安全？

不能。原子 refcount 只保护引用数量，不保证 Block Table、数据复制和状态机整体一致；仍需事务边界、锁/所有权规则与 stream 依赖。

Q29：为什么 page size 不是越小越好？

小页减少内部碎片，但增大页表、索引和 kernel 寻址开销；大页相反。page 16 是当前锁定实现条件，最优值需要按模型和工作负载测量。

Q30：Continuous batching 与静态 batching 区别？

静态 batch 等整组请求全部结束才能换成员，短请求可能等长请求；continuous batching 每次迭代都可加入/移除序列，利用率和响应性更好，但 KV 生命周期和调度更复杂。

Q31：为什么用中位数而非平均数？

Windows/GPU 实验偶发抢占会产生长尾，中位数对少数异常更稳健；但报告仍保留 P95/max 和原始行，不能用中位数隐藏尾部风险。

Q32：置信区间跨 0 说明什么？

当前样本下无法稳定区分正负方向；不能说“完全没有效果”，也不能说“已证明加速”。应继续依据预注册 materiality/promotion gate 作决策。

Q33：为什么选 SQLite 做会话？

单机应用需要事务、索引和可恢复持久化，SQLite 无独立服务且足够可靠。它属于真实用户场景支撑，不是 AI Infra 核心创新。

Q34：SSE 是什么？

Server-Sent Events 是服务器通过一个 HTTP 长连接持续向客户端发送文本事件，适合 token 流。客户端断开要传播 cancellation，避免后台继续占 GPU。

Q35：AI Infra 体现在哪里？

它体现在模型执行周围的基础设施：请求调度、KV 容量/生命周期、GPU kernel、CPU-GPU 异步、性能观测、在线决策与故障回退。Paged Attention 又直接修改模型算子的访存与 softmax，因此兼有模型侧算法。

Q36：如果只让你保留一个亮点？

保留“统一的 evidence-gated KV action runtime”：它把系统状态、CUDA/Attention 动作、在线 Ridge 和可复核实验连起来。Remap 的数据是强证据，Paged 的生产 gate 展示判断力，二者共同支撑完整故事。

11.19 D1 → D2 → D3：为什么模型越来越复杂，却仍然要 fail closed

这一条研究线解决的问题不是“预测哪个动作最快”这么简单，而是：在不同请求状态下，是否有足够证据承担切换动作的风险。一个动作即使平均更快，只要偶尔造成很大的尾延迟伤害，也可能不适合生产默认选择。

D1 是全局线性 Ridge：它假设特征变化对成本的影响近似线性，并用正则化稳定少样本估计。真实回放中它保持安全，但没有产生切换，说明统一直线无法在不确定性门槛下识别可放心启用的局部区域。D2 按 512-token 区间建立 piecewise 模型，让短、中、长 context 能有不同斜率；但 v1.5 中校准 offset 达 7.446 ms，保守门仍然不切换。这不是“模型没运行”，而是估计偏差仍大于可证明收益。

D3 不再只问点预测谁更小：单次 replay 中，候选动作的成本差上界加安全 margin 后仍小于 0 才切换；证据不足就选择 H0。完成整批留出 replay 后，再检查 5% harmful-rate、gain>harm、P95 和 CI 等晋级门。当前选择器没有逐决策扣减的在线 harm budget。这里 regret 指所选动作成本减去同一固定 workload 上 oracle 最低成本；harmful decision 指所选动作成本超过 H0 成本 3% 的决策，不是任意微小变慢。

regret = cost(chosen) − mina∈feasible cost(a)
switch if upper_delta + 0.25 ms < 0
promote only if held-out harmful_rate ≤ 5% and total_gain > total_harm

v1.6 固定了 120 条 trace：60 条拟合、20 条校准、40 条独立评估，共 600 条原始 observation。评估集包含 80 个可比较决策：H0 累计 regret 42.590 ms，D3 为 2.082 ms，下降 95.1%；H0 P95 regret 3.169 ms，D3 为 0；D3 实际切换 24 次，其中 1 次 harmful。总收益 41.480 ms、总伤害 0.972 ms。

“harmful rate”必须带分母：实际观测按全部 eligible decisions 是 1/80=1.25%，按实际 switches 是 1/24=4.17%。材料中的 5% 是实验前注册的晋级阈值，不是第三种观测比例，也不是总体 harmful rate 的 95% 置信上界。matched-workload 的 trace-cluster mean-regret delta 95% CI 为 [−0.7232, −0.3069] ms；区间对象是按 trace 成组重采样的平均 regret 差，而不是单次请求延迟，更不是线上人口效应。

证据边界：四个动作的成本来自独立 fixed-mode 进程，动作与进程身份绑定，因此可能存在 action×process 混杂。D3 结果足以支持进入“同进程 monitored canary”，但不能写成生产因果提速、线上 A/B 或已满足 Trial Pair。下一步是在同一长驻进程内随机或交替执行动作，记录每次策略版本、状态、选择概率和端到端结果。

11A. AI Infra 通用八股：不依赖本项目也要会

这里的 AI Infra（人工智能基础设施）不是“用了 GPU”或“部署了一个模型接口”，而是让模型在给定硬件和服务目标下稳定、经济、可观测地训练或推理的一整套系统。推理方向通常横跨模型计算图、算子、显存管理、调度、分布式通信和在线服务。下面的问题即使面试官不问 CacheFlow，也应能独立回答。

11A.1 一次大模型在线推理分成哪些阶段

  1. 接入与排队：鉴权、限流、路由、排队和取消传播。这里决定 queue time。
  2. Tokenization：把文本转换成 token ID；token 数而非字符数决定模型工作量。
  3. Prefill：一次处理 Prompt 中的大量 token，计算并保存每层 KV。矩阵较大，通常更容易发挥 GPU 计算并行。
  4. Decode：每轮产生一个或少量新 token，同时读取全部历史 KV。单轮矩阵较窄，常更受 KV 读取、launch 和调度影响。
  5. Sampling：模型先输出每个候选 token 的未归一化分数 logits；温度控制分布尖锐程度，Top-k 只保留分数最高的 k 项，Top-p 保留累计概率达到阈值的最小候选集合，最后从处理后的概率中选择下一个 token。
  6. 流式返回：把 token 逐步发送给用户，同时处理断开、取消和错误。

TTFT主要受排队和 Prefill 影响；TPOT主要受连续 Decode 轮次影响；吞吐取决于单位时间内全系统处理的 token 数。优化 Prefill 不一定改善 TPOT，提升吞吐也可能以排队和尾延迟为代价。

11A.2 为什么 Prefill 更像计算密集，Decode 更像访存密集

Prefill 同时处理许多 token，权重可以被一个较大的矩阵乘复用，矩阵乘的算术强度较高。Decode 每轮常只有一个新 token，仍需读取模型权重和整段历史 KV，但能复用这些数据的并行工作较少，因此矩阵更“瘦”，固定开销和内存流量占比更高。这只是常见趋势，不是无需测量的定律；模型大小、batch、量化、算子融合和硬件都会改变瓶颈。

常见追问：为什么扩大 Decode batch 往往提高吞吐？
答案多个 sequence 可共享一次模型权重读取并提供更多并行 CTA，使瘦矩阵变宽、GPU 更饱和；代价是排队、KV 显存和单请求尾延迟可能增加。

11A.3 静态 batching、continuous batching 与 chunked prefill

静态 batching先凑齐一组请求，整组完成后再换成员；实现简单，但短请求会被长请求拖住。Continuous batching在每个推理迭代重新选择成员，完成的 sequence 可立即离开，新请求可加入。Chunked prefill把长 Prompt 拆成多个 chunk，使它们与 Decode 交错，避免一个超长 Prefill 长时间阻塞在线用户。

策略优势主要代价
静态 batch实现和图形状简单Head-of-line blocking，利用率受最长请求限制
Continuous batch成员动态变化，吞吐和响应性更好KV 生命周期、调度和 CUDA Graph 更复杂
Chunked prefill降低长 Prompt 对 Decode 的阻塞更多迭代/launch，chunk 太小会损失 Prefill 效率

Head-of-line blocking（队头阻塞）指队列前面的慢任务阻止后面的快任务，即使后者本可立即完成。调度器常需要在 Decode 优先、Prefill 吞吐、deadline、公平和显存之间权衡。

11A.4 KV Cache 为什么是服务系统的核心状态

自回归 Decode 若不保存历史 K/V，每生成一个 token 都要重新计算全部历史；KV Cache 用显存换计算。它的容量随层数、KV Head 数、Head Dimension、数据类型字节数、上下文长度和活跃 sequence 数近似线性增长。GQA/MQA 通过让多个 Query Head 共享较少 KV Head，主要减少 KV 容量和读取量，而不是减少 Query Head 数。

常见优化包括：

  • Paged KV：用固定页和 Block Table 管理非连续物理内存。
  • Prefix caching：复用相同 Prompt 前缀已经计算好的 KV。
  • KV quantization：用更低位宽保存 K/V，降低容量和带宽，但需控制精度损失与反量化成本。
  • Offload/Swap：把冷 KV 移到 CPU 或其他设备，以传输延迟换 GPU 容量。
  • Evict/Recompute：丢弃低价值 KV，需要时重新 Prefill。

面试回答不能只说“PagedAttention 节省显存”，还应说明它将逻辑连续与物理连续解耦，主要缓解外部碎片和过度预留，同时引入页表、间接寻址和更复杂生命周期。

11A.5 模型并行：DP、TP、PP、EP 分别是什么

Data Parallelism（DP，数据并行）让多张卡各保存完整模型，分别处理不同请求；推理中扩展吞吐直接，但单个模型必须能放入一张卡。Tensor Parallelism（TP，张量并行）把同一层的矩阵沿维度拆到多卡，每层都需要 All-Reduce/All-Gather 等通信；能容纳更大模型，但 Decode 的频繁小通信可能昂贵。Pipeline Parallelism（PP，流水线并行）把不同层放到不同设备，让 micro-batch 像流水线一样经过各阶段；会产生 pipeline bubble。Expert Parallelism（EP，专家并行）用于 MoE（Mixture of Experts，混合专家模型：每个 token 只激活一部分子网络），将不同专家放在不同设备，请求 token 经路由后发生 All-to-All 通信。

方式拆什么主要通信/问题
DP请求负载均衡、实例间缓存不共享
TP单层张量每层 collective，受延迟和带宽影响
PP模型层阶段不平衡与 pipeline bubble
EPMoE 专家路由不均衡与 All-to-All

Collective communication（集合通信）是多设备共同参与的数据交换。All-Reduce 汇总各卡数据并把结果发回所有卡；All-Gather 收集各卡分片；Reduce-Scatter 先归约再分片；All-to-All 让每张卡分别向所有其他卡发送不同分片。选择并行策略必须结合模型是否装得下、互联带宽、batch、延迟目标和容错成本。

11A.6 量化到底优化了什么

量化用更少 bit 表示权重、激活或 KV，例如 FP16、INT8、INT4。它可能降低模型容量和显存带宽，也可能让 Tensor Core（GPU 中专门加速小矩阵乘加的硬件单元）使用更高吞吐的数据类型；但必须保存 scale（把整数映回实数的缩放系数）和可选 zero-point（实数零对应的整数位置），并付出量化/反量化指令与精度风险。

  • Weight-only quantization：主要压缩权重；计算前按块反量化，适合 Decode 中权重带宽占比较高的场景。
  • Weight-activation quantization：权重和激活都降低位宽，可获得更高计算吞吐，但校准和异常值处理更难。
  • KV quantization：直接减少随上下文增长的 KV 容量和读取量，但误差会影响每一轮 Attention。

Calibration（校准）是用代表性数据确定量化尺度或裁剪范围；数据分布不代表线上请求时，离群激活可能导致明显误差。评价量化至少同时看模型质量、TTFT、TPOT、吞吐、峰值显存和支持的最大上下文。

11A.7 FlashAttention、PagedAttention 与算子融合的区别

FlashAttention主要通过分块和在线 softmax，减少 Attention 中间矩阵在高带宽显存中的读写，属于计算/IO 算法优化。PagedAttention主要解决 KV 的分页布局和非连续访问，属于内存管理与 Attention 地址访问结合。二者可以组合：分页决定 K/V 从哪里读，Flash 风格算法决定如何分块计算而不物化完整 score 矩阵。

Kernel fusion（算子融合）把原本多个 kernel 的中间结果留在寄存器/shared memory 中，减少 launch 与显存往返。例如把 bias、activation、residual 合并。但融合过度会增加寄存器和 shared memory 使用，降低 occupancy，或让编译形状过于专用。

11A.8 Speculative decoding 为什么可能加速

Speculative decoding（推测解码）先用更便宜的 draft 方法提出多个候选 token，再由目标模型一次验证。只要接受/拒绝规则正确，输出分布可以与目标模型保持一致。它减少的是目标模型串行 Decode 轮数，不一定减少目标模型每次验证的计算量。

期望收益取决于：一次提出 token 数 × 接受率 × 验证并行效率 总成本还包括：draft 成本 + verify 成本 + rejection 后的浪费

接受率低、draft 太慢或 batch 调度不匹配时可能负优化。常见实现有小模型 draft、N-gram/Prompt lookup 和多分支 tree speculation。评价时要报告接受长度、接受率、目标模型调用次数、TPOT 和尾延迟，不能只报告 draft 命中率。

11A.9 CUDA Graph、算子编译与动态形状

CUDA Graph把一串重复 kernel/memcpy 调用捕获为可复用图，降低每轮 CPU launch 开销。难点是地址、shape、batch 成员和 workspace 可能动态变化。常见办法是按容量/拓扑建立多个 graph bucket，或捕获最大容量图并用设备侧有效长度屏蔽无效工作。

Graph key 不完整会复用错误图；key 太细又会产生大量图、占用内存并频繁重捕获。生产系统通常在“动态灵活性”和“低启动开销”之间分桶。类似地，JIT（Just-In-Time，即运行时即时编译）和 shape specialization（针对固定张量形状生成专用代码）可让编译器消除部分动态判断，但会带来首次编译延迟和编译缓存管理。

11A.10 AI 推理服务的可靠性八股

  • Backpressure：容量不足时拒绝或延迟接入，防止队列无限增长。
  • Timeout/Deadline：请求超过价值窗口后停止占用 GPU；取消必须传播到 scheduler 和模型流。
  • Load shedding：过载时主动丢弃低优先级工作，以保护核心 SLO。
  • Fail closed：候选优化证据不足或能力不匹配时回到安全基线。
  • Idempotency：重试同一请求不会重复提交不可撤销副作用；流式生成通常需要请求 ID 与状态记录。
  • Isolation：租户的配额、缓存键和指标不能串扰；模型版本变化后旧 KV 不能直接复用。
  • Graceful degradation：GPU/Swap/候选 kernel 失败时选择较慢但正确的路径，而不是返回静默错误。

11A.11 容量规划与必须会算的三个关系

Little 定律：平均并发 L = 到达率 λ × 平均停留时间 W 利用率接近 100% 时，排队延迟通常会非线性上升； 所以生产容量不能只按峰值算力恰好打满。 可容纳 sequence 数 ≈ 可用于KV的显存 / 平均每sequence KV字节 实际还要扣除权重、workspace、graph、碎片和安全余量。

Little 定律连接吞吐和并发：若系统每秒完成 10 个请求、平均每个请求停留 2 秒，则系统内平均约有 20 个请求。它不要求特定到达分布，但要求观察窗口内系统相对稳定。容量规划还要使用真实长度分布和 P95/P99，而不是只用平均 Prompt。

11A.12 通用 AI Infra 高频快问快答

Q：吞吐和延迟为什么常冲突？

等待更多请求组成大 batch 能提高权重复用和 GPU 利用率，却增加排队时间；服务需要在吞吐收益与 TTFT/TPOT SLO 之间选择 batch 上限和等待窗口。

Q：为什么 Decode 常比 Prefill 更难把 GPU 跑满？

每条 sequence 每轮只有少量新 token，矩阵较窄、串行轮次多，权重/KV 读取与 launch 成本难以摊薄；扩大 active sequence batch 可以改善，但会增加 KV 容量和调度复杂度。

Q：为什么不能用 GPU utilization 一个指标判断优化？

利用率通常只表示一段时间 GPU 有工作，不说明 Tensor Core、带宽或有效吞吐是否高；无效 kernel、忙等或更长执行也能提高利用率。应结合 tokens/s、延迟、功耗和硬件计数。

Q：什么时候选 TP，什么时候选 DP？

模型能放入单卡且目标是扩吞吐时优先 DP；模型放不下或单请求计算需要多卡时使用 TP/PP。TP 引入每层通信，对低 batch Decode 尤其敏感。

Q：PagedAttention 与操作系统虚拟内存完全一样吗？

不完全一样。二者都用逻辑到物理映射，但 GPU PagedAttention 的页通常由用户态运行时显式管理，没有普通 CPU 缺页异常、磁盘透明换页和硬件 TLB 的完整语义。

Q：如何证明一次优化可上线？

先证明输出/质量等价和失败回退，再在代表性负载下比较端到端指标与资源指标，预注册尾部和最差场景门槛，最后通过 canary（先只让极少量真实流量进入候选版本的灰度验证）观察真实表现；microbenchmark 只能证明局部机制。

11A.13 Prefill/Decode 分离与分布式服务

Prefill-Decode disaggregation（Prefill/Decode 分离）把计算形态不同的两个阶段放到不同实例池：Prefill 池偏向高计算吞吐，Decode 池偏向低延迟和高内存带宽。Prefill 完成后必须把 KV 传给 Decode worker，因此收益取决于调度改善能否覆盖 KV 传输、排队和失败恢复成本。

请求 → Prefill worker → KV transfer → Decode worker → token stream ↑ 路由必须知道容量、模型版本和缓存位置

PCIe是主机与 GPU/设备常用互联；NVLink是 NVIDIA GPU 间更高带宽的互联；RDMA允许网络设备直接访问远端内存，减少 CPU 拷贝。带宽决定大块数据传输时间，链路延迟决定频繁小通信成本。TP 每层的小 collective 对延迟敏感，KV migration 则同时受总字节数和带宽影响。

分布式 Prefix Cache 还会带来路由问题：把请求送到已有相同 Prefix 的实例可以节省 Prefill，但可能造成热点和负载不均。调度目标会变成“缓存亲和性收益”与“队列/容量代价”的联合优化，而不是简单一致性哈希。

11A.14 可观测性：从一条慢请求追到 GPU

可观测性是从系统输出推断内部状态的能力，通常结合 metrics、logs 和 traces。Metrics 适合聚合趋势；logs 记录离散事件和错误上下文；trace 用同一 request ID 串起跨模块时间段。一次慢请求至少应能分解：

admission wait → scheduler queue → tokenize → prefill → KV action → decode iterations → sampling → network flush

关键指标可分为：

  • 流量：requests/s、input/output tokens/s、active sequences。
  • 用户延迟：TTFT、TPOT/TBT、端到端 P50/P95/P99。
  • 容量：KV used/free blocks、峰值显存、queue length、rejection/OOM。
  • 执行：batch size、Prefill chunk、kernel/event time、GPU idle gap。
  • 正确性与稳定性：fallback、cancel、timeout、error、重试和输出一致性。

高基数标签会让监控系统爆炸，因此 request ID 通常进入 trace/log，而不是直接作为 Prometheus 长期标签。模型、backend、action、reason 等有限枚举更适合作为 metric label。

11A.15 另外十个常见追问

Q：为什么量化后模型变小却不一定更快？

硬件可能缺少对应低位算子，反量化和布局转换可能抵消带宽收益，小 batch 又可能受 launch 而非权重读取限制；必须看实际 kernel 和端到端指标。

Q：为什么 TP 卡数不是越多越快？

每张卡计算量下降，但每层 collective 的固定延迟和通信比例上升；当通信超过节省的计算时继续加卡会负扩展。

Q：什么是 pipeline bubble？

流水线某些 stage 因前后阶段尚无可处理 micro-batch 而空闲的时间。增加 micro-batch 可降低 bubble 比例，但会增加内存和请求延迟。

Q：Prefix Cache 为什么可能降低命中却提高整体性能？

若为了命中把请求路由到长队列实例，节省的 Prefill 可能小于新增排队；负载感知路由可能主动放弃局部命中，换取更低 TTFT。

Q：什么是 preemption？

抢占是暂停或移出已占资源的低优先级 sequence，为更重要工作腾出容量。被抢占 KV 可 Swap，也可丢弃后 Recompute；选择取决于恢复成本。

Q：为什么 P99 很重要但难测？

P99 对少量极慢请求敏感，直接对应严重用户体验；但需要足够大样本，否则只是最大值附近的少数点，置信度很低。应报告样本量和区间。

Q：什么是 goodput？

Goodput 是满足质量与 SLO 的有效吞吐；超时、错误或延迟超标的完成量不能算有效服务能力。它比只看 tokens/s 更接近生产价值。

Q：为什么需要按模型版本隔离 KV Cache？

不同权重、RoPE 参数、KV dtype 或布局生成的 K/V 语义可能不同；错误复用可能输出看似正常但实际错误，因此缓存键必须绑定模型与布局身份。

Q：线上扩容应该看 GPU 利用率还是队列？

二者都不够。应结合排队延迟、active sequences、KV 容量、TTFT/TPOT SLO 和 goodput；GPU 利用率高可能是健康繁忙，也可能是慢 kernel 或过载。

Q：AI Infra 优化的最终判断标准是什么？

在输出质量和可靠性不下降的前提下，用更少硬件成本满足更多真实请求的 SLO。局部 FLOPS、带宽或 kernel time 都只是解释这一目标的中介指标。

11A.16 训练侧 AI Infra：与推理有什么不同

训练需要前向计算、保存中间激活、反向传播梯度并更新参数；推理通常只有前向计算和动态 KV。训练显存常近似包含权重、梯度、优化器状态、激活和临时 workspace。其中 Adam 是一种为每个参数维护梯度一阶动量与二阶平方动量的优化算法，因此它的优化器状态可能比低精度权重本身更大。

  • Mixed precision（混合精度）：主要矩阵计算用 FP16 或 BF16，关键累积或主权重保留更高精度。BF16（Brain Floating Point 16）是一种 16 位浮点格式，保留与 FP32 相同宽度的指数位，因此指数范围接近 FP32，通常比 FP16 更不易溢出；FP16 常配合 loss scaling（损失缩放），先把过小梯度放大以避免下溢，计算后再按比例缩回。
  • Gradient accumulation（梯度累积）：连续运行多个 micro-batch，把梯度相加后才更新一次参数，用更多计算轮次模拟更大 global batch，不会降低单个 micro-batch 的激活峰值。
  • Activation checkpointing（激活重计算）：前向只保存部分检查点，反向需要时重新计算中间激活，以额外计算换显存。
  • Distributed Data Parallel（分布式数据并行）：每张卡处理不同数据并计算局部梯度，再用 All-Reduce 使各卡得到一致梯度。
  • ZeRO：把优化器状态、梯度乃至参数分片到不同数据并行 rank（参与分布式任务的进程编号），避免每卡完整复制。分片越彻底，显存越省，但通信与实现复杂度越高。

Global batch通常等于每卡 micro-batch × 数据并行卡数 × 梯度累积步数。扩大 global batch 可提高吞吐，却可能改变优化统计性质和收敛，因此训练系统不能只看 samples/s（每秒处理的样本数），还要看 loss（训练目标函数的数值）、收敛步数、故障恢复和最终质量。

训练容错依赖 checkpoint：需要保存模型、优化器、学习率调度器、随机数状态和数据迭代位置，才能尽量从相同训练状态恢复。大规模训练中 checkpoint 写入本身可能造成 I/O 停顿，因此会使用异步保存、分片和增量策略。
